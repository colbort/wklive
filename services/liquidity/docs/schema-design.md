# 流动性服务 SQL 设计说明

## 设计范围

第一版同时为三种模式预留数据模型：

1. 内部做市：平台或第三方做市用户向 `trade.rpc` 的内部订单簿挂双边限价单。
2. 外部路由：用户订单路由到外部交易场所并接收成交回报。
3. 内部做市并外部对冲：内部成交产生净敞口后，在外部交易场所对冲。

秒合约不进入本服务。秒合约属于平台赔付和敞口风控，不依赖订单簿流动性。

## 表分组

### 配置

- `t_liquidity_provider`：内部做市账户或外部流动性账户。
- `t_liquidity_symbol_config`：交易对模式、行情、报价、库存和对冲限制。
- `t_liquidity_strategy_level`：多档买卖报价参数。

### 内部报价

- `t_liquidity_quote_cycle`：每次行情驱动的重新报价执行记录。
- `t_liquidity_quote_order`：目标报价与 `trade` 内部订单之间的映射。

### 外部路由与对冲

- `t_liquidity_external_order`：外部下单、撤单和状态恢复。
- `t_liquidity_external_fill`：外部成交回报及内部入账状态。
- `t_liquidity_hedge_task`：净敞口对冲任务。

### 库存与风险

- `t_liquidity_inventory_snapshot`：内部、外部或合并库存及敞口快照。
- `t_liquidity_risk_event`：余额不足、行情过期、偏离、限额和熔断事件。

### 对账

- `t_liquidity_reconcile_batch`：订单、成交、余额和持仓对账批次。
- `t_liquidity_reconcile_detail`：逐条差异及修复状态。

### 可靠事件

- `t_liquidity_event_inbox`：消费幂等和失败恢复。
- `t_liquidity_event_outbox`：事务内事件落库和可靠发布。

## 关键决策

- 跨服务数据不使用数据库外键，依赖业务校验和事件对账。
- 做市账户必须是专用 `trade_user_id`，不能与普通用户混用。
- 外部密钥由密钥管理系统托管，数据库只保存引用。
- 外部成交先幂等落库，再执行内部资产或持仓入账。
- 报价必须有 `expire_at`，行情过期、服务失联或熔断时可统一撤单。
- `version` 用于配置、订单和任务的乐观锁。

## 审核重点

1. 是否第一期只保留内部做市，暂缓外部路由与对账表。
2. 是否允许一个交易对绑定多个内部做市提供方。
3. 现货库存是否按基础币/计价币管理，合约是否统一按保证金资产和净持仓管理。
4. 报价档位使用固定数量，还是支持按名义金额和随机区间生成。
5. 外部凭证是否已有统一密钥管理服务及 `credential_ref` 格式。
6. 对账差异是否允许自动修复，还是第一期只告警并人工处理。
