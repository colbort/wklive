> 文档状态：本轮服务端整改及本地验收完成，生产观察项待执行

> 适用范围：`services/staking`、Staking Proto、Asset 资金依赖、`admin-api`、`admin-ui`、`app-api`、数据库及调度任务  
> 结论：STK-P0-001～008 和 P1 服务端整改已完成，并通过单元测试、构建、真实数据库迁移及本地全链路验收。当前未完成项是 App Web/Mobile 的 P2 产品页面、生产环境连续日对账观察和 10 万活跃订单容量压测；这些项目完成前不得直接宣称“生产上线验收完成”。

## 1. 业务边界

Staking 服务负责：

1. 租户质押产品的创建、配置、上下架和查询；
2. 用户按产品规则锁定资产并生成质押订单；
3. 按产品快照计算、发放或累计收益；
4. 到期赎回、提前赎回和后台人工补偿操作；
5. 记录每一笔本金、收益、手续费和失败重试；
6. 为总后台管理员提供全租户管理，为租户管理员提供严格的本租户管理；
7. 在进程重启、消息丢失、RPC 超时及部分失败后自动恢复，不重复增减资产。

以下内容不属于本轮服务端验收范围：App Web/Mobile 的完整质押产品交互页面。`app-api` 的用户接口属于本轮范围，前端产品页面作为独立交付项列入 P2。

## 3. P0 上线阻断缺口

### STK-P0-001 时间字段溢出

- 证据：订单、收益和赎回业务时间字段在 SQL 中使用 `INT`，代码写入 `utils.NowMillis()` 毫秒时间戳。
- 风险：毫秒时间戳超过 MySQL 有符号 `INT`，创建订单、收益或赎回时可能报错或产生无效时间。
- 整改：所有毫秒时间字段统一改为 `BIGINT NOT NULL DEFAULT 0`；提供可重复执行的迁移；修改后执行 `make gen-model`，不得手工长期维护旧生成模型。
- 验收：插入当前及未来 20 年的毫秒时间，读写值一致；旧数据迁移无截断。

### STK-P0-002 后台租户越权与审计身份伪造

- 证据：多个 Admin List/Detail/Create RPC 仅在请求 tenantId 为空时读取登录租户；租户管理员显式传入其他 tenantId 时可越权。`operator_uid` 由前端输入。
- 风险：跨租户查看或操作产品、订单、收益、赎回；操作审计责任人可伪造。
- 整改：
  - 所有读接口统一调用 Admin tenant read scope；
  - 所有写接口统一调用 Admin tenant write scope；
  - 总后台可指定任意租户或查询全部租户；租户管理员只能使用登录租户；
  - operator UID 从可信登录元数据写入，忽略前端传值；
  - 产品禁止通过更新接口迁移租户。
- 验收：覆盖总后台、本租户、跨租户、tenantId=0、缺少元数据五组用例，跨租户全部被拒绝。

### STK-P0-003 创建质押的幂等和并发额度

- 证据：创建订单没有 `request_no`；产品总额度与用户额度采用“先查后写”，没有行锁、CAS 或条件更新。
- 风险：客户端重试造成重复锁仓；并发订单超卖产品额度、突破用户额度或覆盖 `staked_amount`。
- 整改：
  - CreateOrder 增加必填 `request_no`，数据库建立 `(tenant_id,user_id,request_no)` 唯一约束；
  - 订单号由幂等请求确定，重复请求返回原订单；
  - 产品额度使用原子条件更新；用户限额在事务内加锁并复核；
  - Asset Lock 使用确定性业务号并具备幂等约束；
  - DB 失败后的解锁进入持久化恢复流程，不能只记录日志。
- 验收：同一请求并发 20 次仅生成一个订单、一次锁仓；额度仅剩一单时并发 20 次只成功一单。

### STK-P0-004 赎回并发、幂等与跨服务资金一致性

- 证据：赎回依次调用解锁本金、扣手续费、发收益，再更新 Staking 数据库；没有处理中状态、CAS 和恢复指令。
- 风险：并发重复赎回；某一步成功后下一步失败导致本金、手续费、收益和订单状态永久不一致。
- 整改：
  - Redeem/ManualRedeem 增加 `request_no`；
  - 新增持久化资金操作记录，先落操作单，再执行外部资金步骤；
  - 本金、手续费、收益分别使用不同且确定的幂等业务号；
  - 每一步记录状态，最终以订单版本 CAS 收口；
  - 后台任务自动重试未完成步骤，达到上限进入人工处理；
  - 第一阶段只支持整单赎回，人工赎回金额必须等于订单本金，禁止“部分解锁但整单结束”。
- 验收：对每个 RPC 步骤注入超时/失败并重启服务，最终只发生一次正确资金变化；并发赎回仅一个请求进入处理。

### STK-P0-005 奖励发放幂等与人工奖励重复记账

- 证据：人工奖励始终以 `order_no` 调用 Asset AddAvailable。Asset 将其视为同一幂等请求，第二次不入账，但 Staking 仍增加累计收益并写成功日志。
- 风险：Staking 显示已发收益大于用户真实余额，形成直接账实差异。
- 整改：
  - ManualReward 增加唯一 `request_no`；每笔奖励生成独立 operation number；
  - 奖励操作、资金业务号和收益日志一一对应；
  - 重复 request_no 返回原结果，不重复增加订单累计收益；
  - 只允许合法订单状态发奖励；
  - 外部入账成功而 DB 未完成时由恢复任务补写，不再次入账。
- 验收：同请求重放不重复入账；不同请求可分别入账；在 Asset 成功后模拟 DB 失败可自动恢复且账实一致。

### STK-P0-006 到期结算失败日志阻断重试

- 证据：到期结算失败插入唯一 `redeem_no` 的失败记录；重试成功后再次插入同一 `redeem_no` 会冲突。
- 风险：一次临时故障可能让订单永久无法完成到期赎回。
- 整改：失败与成功更新同一操作记录；日志采用状态迁移/Upsert，禁止用重复插入表达重试；订单增加明确的处理中和失败可重试语义。
- 验收：首次失败、第二次成功能够正常完结，数据库仅有一条操作主记录并保留完整尝试历史。

### STK-P0-007 周期任务缺失与延迟队列不可恢复

- 证据：当前数据库未找到 `staking.*` 的 `sys_job`；创建订单时延迟队列发送失败只写日志。
- 风险：没有日收益任务；队列或节点异常后订单不会准时结算。
- 整改：
  - 合并 SQL 中加入 Staking 扫描任务；
  - 周期扫描作为权威兜底，延迟队列仅用于降低延迟；
  - 扫描支持分页、租户分片、锁续期和可观测指标；
  - 队列投递失败写入持久操作/重试表。
- 验收：关闭队列后只依赖周期任务仍能完成收益和到期结算；任务重复执行不重复入账。

### STK-P0-008 奖励来源与手续费去向缺少会计闭环

- 证据：奖励直接 AddAvailable，手续费直接从锁定资产扣减，没有对应租户奖励账户、平台账户或负债流水。
- 风险：资产被无来源增发或无去向销毁，无法对账和审计。
- 整改：
  - 明确“租户奖励资金账户”和“租户手续费收入账户”；
  - 优先采用账户间转账；若 Asset 暂不支持，则必须同步记录平台负债/收入流水并纳入日对账，禁止无依据记账；
  - 产品上线前校验奖励资金配置与余额策略。
- 验收：任一质押操作满足用户资产变化 + 平台/租户账户变化 = 0（已批准的发行型资产除外），日对账无差额。

## 4. P1 功能和可维护性缺口

### STK-P1-001 产品规则校验

必须校验：租户、产品名称和币种必填；枚举合法；APR/费率范围；`min <= max <= user_limit <= total` 的适用关系；步长与币种精度；锁定天数与产品类型、收益模式组合；总额度不得低于已质押额度；已产生订单后禁止直接修改核心经济参数。

产品订单继续保存完整快照，历史订单不得随产品修改而变化。

### STK-P1-002 计息语义、补算与精度

- 明确定义计息起点、日切时区、365/360 日基准、舍入模式和最小发放单位；
- `interest_mode` 必须实际参与逻辑或从模型中删除，禁止“配置存在但不生效”；
- 周期任务延迟多天时按原 `next_reward_times` 循环补齐，不得按当前时间只补一天；
- 到期前先补齐全部应计周期，再完成本金结算；
- 金额计算全程 Decimal，落账前按币种精度统一舍入。

### STK-P1-003 后台页面

- 总后台可选择租户；租户后台固定为登录租户且不可篡改；
- 产品、订单、收益日志、赎回日志使用分页查询；
- 操作按钮根据订单/产品状态显示可用或禁用；
- 删除人工填写 operator UID；
- 人工奖励/赎回弹窗显示币种、可操作金额、费率、预计到账和二次确认；
- 详情使用字段化展示，不再直接输出 JSON；
- 金额按币种精度显示，后台可在详情查看原始精度。

### STK-P1-004 对账、告警与人工恢复

- 增加订单本金、用户锁仓、累计收益、奖励流水、赎回流水的日对账；
- 指标至少包括待处理操作数、失败操作数、最大延迟、任务耗时、入账失败率、对账差额；
- 后台提供失败操作详情和安全重试入口；
- 告警包含 tenant、order、operation、step、error code，不输出敏感凭据。

### STK-P1-005 错误码与接口契约

- 业务错误使用稳定错误码，不依赖英文错误文本；
- 列表接口统一 page/limit/total；
- 金额继续使用字符串传输；
- Proto 变更后同步生成 RPC、Admin API、App API 和前端类型，并做兼容期处理。

## 6. 目标数据与状态设计

### 6.1 订单状态原则

业务主状态保持清晰，资金执行状态由独立操作单承载：

```text
CREATED -> STAKING -> REDEEMED
                  -> EARLY_REDEEMED
                  -> CANCELLED（仅未完成锁仓时）
```

不得为了每一个 RPC 步骤不断扩充订单枚举。订单只有在资金操作全部确认后才进入终态。

### 6.2 资金操作单

新增 `t_stake_operation`，至少包含：

| 字段 | 说明 |
| --- | --- |
| operation_no | 全局唯一操作号 |
| request_no | 客户端/后台幂等号 |
| tenant_id / user_id / order_id | 归属范围 |
| operation_type | SUBSCRIBE、DAILY_REWARD、MATURITY_REDEEM、EARLY_REDEEM、MANUAL_REWARD 等 |
| principal_amount / reward_amount / fee_amount | 本次资金组成 |
| principal_status / reward_status / fee_status | 每个资金步骤状态 |
| status | PENDING、PROCESSING、SUCCEEDED、RETRYABLE_FAILED、MANUAL_REQUIRED |
| retry_count / next_retry_at / last_error | 恢复信息 |
| version | CAS 版本 |
| create_times / update_times | 毫秒时间 |

唯一约束：

- `(tenant_id, operation_no)`；
- 对用户请求：`(tenant_id, user_id, operation_type, request_no)`；
- 对周期收益：`(tenant_id, order_id, operation_type, period_end)`。

每一个 Asset 调用使用不同业务号：

```text
{operation_no}:principal
{operation_no}:fee
{operation_no}:reward
```

### 6.3 操作执行顺序

```text
请求校验
  -> 本地事务创建/取得幂等操作单
  -> CAS 抢占操作执行权
  -> 执行尚未完成的 Asset 步骤
  -> 每一步持久化成功状态
  -> 本地事务更新订单、产品和业务日志
  -> 操作单 SUCCEEDED
```

超时按“结果未知”处理：使用相同幂等业务号重试或查询结果，不能换新业务号重复发起。

## 9. 测试方案

### 9.1 单元测试

- 产品组合校验边界；
- APR、日收益、到期收益、提前赎回费和舍入；
- 补算 0/1/N 天；
- 订单和操作状态迁移；
- tenant read/write scope；
- operation/business number 的稳定性和唯一性。

### 9.2 数据库测试

- 毫秒 BIGINT；
- 幂等唯一键；
- 原子额度更新；
- 同一订单并发赎回 CAS；
- 失败记录 Upsert 后可成功收口；
- migration 可重复执行或具备明确版本保护。

### 9.3 Asset Fake 故障注入

对 Lock、Unlock、Deduct、Add/Transfer 的每一步覆盖：

1. 成功；
2. 明确失败；
3. 调用前超时；
4. 资金已变更但响应超时；
5. Staking DB 更新失败；
6. 服务重启后恢复；
7. 同请求并发和重复投递。

断言必须同时检查：订单、产品已质押额、操作单、收益/赎回日志、用户余额、锁仓、平台/租户账户和资产流水。

### 9.4 RPC 与权限集成测试

- 总后台查询全部租户和指定租户；
- 租户管理员本租户成功，跨租户被拒绝；
- App 用户只能访问自己的订单；
- 伪造 tenantId、userId、operatorUid 无效；
- 分页、过滤、空数据和错误码一致。

### 9.5 前端验收

- 两类管理员登录；
- 产品 CRUD/上下架；
- 订单查询、详情、人工奖励、整单人工赎回；
- 状态不允许时按钮禁用并解释原因；
- 金额、时间、空状态、加载状态、错误提示和分页正常；
- 浏览器控制台无报错、无缺少组件、无乱码。

### 9.6 恢复与性能

- 关闭延迟队列，只运行扫描任务；
- 任务运行中重启 Staking、Asset、Redis；
- 重复 Kafka/定时任务消息；
- 10 万活跃订单分页扫描，不全表装载；
- 同产品高并发质押不超卖；
