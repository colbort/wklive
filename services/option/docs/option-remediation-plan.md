# Option 整改实施与验收计划

## 1. 使用方式

本文是 `services/option` 的实施台账。设计依据见
[`option-design-review.md`](option-design-review.md)，运行与应急流程见
[`option-operations-runbook.md`](option-operations-runbook.md)。

状态定义：

- `TODO`：尚未实施。
- `DOING`：正在实施，不能作为已完成能力。
- `VERIFYING`：代码完成，等待完整验收证据。
- `DONE`：实现、迁移、测试、文档和验收证据全部完成。
- `EXTERNAL`：需要外部平台或业务决策；仓库内可准备内容已完成。
- `DEFERRED`：不属于当前产品范围且无可调用入口；满足表内进入条件后重新立项，不作为当前上线阻断。

任何项目只有在“验收标准”全部满足并记录证据后才允许改为 `DONE`。

## 2. 发布原则

1. P0 全部完成前，Option 只能用于模拟盘和开发联调。
2. 任何卖方产品上线前，P0、卖方相关 P1 和生产运行门禁必须完成。
3. 组合保证金、美式行权、实物交割分别独立验收，不因欧式现金通过而自动开放。
4. 功能开关默认关闭；没有明确完成证据的能力不能由运营配置绕过。
5. 迁移必须可重复执行，历史数据必须有校验和回滚/前滚方案。

## 3. P0 资金与清算正确性

### OPT-P0-001 统一风险账户与 Asset 钱包范围

- 状态：`VERIFYING`
- 问题：Option 按 `account_id` 计算风险，Asset 按用户钱包保存余额，同一余额可能被多个风险账户重复使用。
- 目标设计：Option 风险权益按 `(tenant_id, user_id, settle_coin)` 用户钱包级聚合；业务订单和持仓仍可保留 `account_id` 作为策略/展示维度，但不能形成独立资金池。
- 修改范围：
  - 风险账户使用固定资金池账户标识，不再按业务 `account_id` 重复读取余额。
  - 组合保证金准入聚合该用户全部 Option 账户的持仓、活动订单和保证金批次。
  - 下单检查用户钱包级风险状态。
  - 自成交保护至少按 `user_id` 生效，不能用不同 `account_id` 绕过。
  - 管理端/API 明确 `account_id` 不代表独立资金子账户。
- 验收标准：
  - 同一用户两个 `account_id`、同一币种只产生一个风险权益总额。
  - 两账户卖方头寸的维持保证金均计入同一风险账户。
  - 任一账户触发用户钱包风险限制后，两账户均不能增加风险。
  - 组合保证金订单准入不能通过拆分 `account_id` 获得额外抵扣或重复余额。
  - 跨账户同用户订单不能成交。
  - 单元测试、MySQL 集成测试和 Asset RPC 端到端测试通过。
- 当前结果：

### OPT-P0-002 修正净清算权益公式

- 状态：`VERIFYING`
- 问题：当前使用 `Asset total + unrealized PnL`，权利金已经进入 Asset 后会被重复计算。
- 目标公式：

```text
equity = Asset total
       + long option mark value
       - short option mark value
       + confirmed pending adjustments
```

- 修改范围：
  - 风险扫描独立累计期权净市值。
  - `unrealized_pnl` 继续作为展示指标，不参与重复计价。
  - 风险账户增加或复用可审计字段记录净期权市值。
  - 补充多头、空头、价差、部分平仓、费用、行权和到期恒等式测试。
- 验收标准：
  - 多头支付权利金后，在标记价不变时净清算权益不变（忽略手续费）。
  - 空头收到权利金后，在标记价不变时净清算权益不变（忽略手续费）。
  - 标记价变化一单位时，权益按净 Delta 数量的线性持仓市值变化。
  - 多空同数量同合约完全对冲时，净期权市值为 0。
  - 风险率和强平触发使用新权益。
- 当前结果：
  - 除既有公式/屏障单测外，真实 Asset gRPC 已证明权利金完成入账后的买方与卖方在标记价不变时
    权益均回到1000；跨账户组合按净市值 `+20-10` 只计算一次钱包余额。
  - 开仓权利金、手续费、真实撮合部分平仓、主动行权、混合 AUTO/DNE 到期和逐仓整仓/自动部分数量强平的真实 Asset 会计流水已通过，
    且钱包净变动、剩余/接管仓位市值、持仓分项收益与平台费用守恒。隔离 Call 已从公开
    `PlaceOrder/CancelOrder` 完成五类普通单和用户撤单：IOC成交1/2并释放剩余10.4，FOK不足零成交，
    MARKET预留12后消费10.4/释放1.6，POST_ONLY会吃单零成交、不吃单入簿；共30条新增订单链指令中
    29条成功对账，1条冻结前合法取消且无流水。逐仓整仓穿仓的保险/平台兜底及响应丢失恢复也已通过。
    现金USDT管理强撤及20轮撤单—冻结竞态随后也已通过；组合保证金整仓顺序清算已经通过；组合部分数量也完成
    情景模型选量代码、严格边界/网格上限单测、静态门禁和真实 Asset RPC，2张自动选1张且4条清算指令对账。
    跨币种、保险库存主动退出和全币种
    及同仓位继续行权/到期/强平仍须按 EQ-003/004 及后续清算用例
    在预生产执行，故保持 `VERIFYING`。

### OPT-P0-003 拆分行情来源与新鲜度

- 状态：`VERIFYING`
- 问题：标的价、标记价和 Greeks 共用 `snapshot_time`，标的更新会掩盖标记价陈旧。
- 修改范围：
  - `t_option_market` 增加 `underlying_snapshot_time`、`mark_snapshot_time`、`greeks_snapshot_time`。
  - 保留旧 `snapshot_time` 作为兼容字段，迁移期只表示整条记录最后可用时间，不再用于风险判定。
  - 标的消费者只更新标的时间；成交/定价引擎只更新标记价时间；Greeks 单独更新。
  - 下单、组合保证金、风险扫描、主动行权分别检查所需输入时间。
- 验收标准：
  - 仅刷新标的价不能让陈旧标记价通过风险检查。
  - 仅刷新标记价不能让陈旧标的价通过行权或保证金检查。
  - 数据迁移后未能证明时间来源的旧记录默认不可用于卖方新开仓。
  - 新旧 API 兼容，管理端可看到各时间戳和过期状态。
- 当前结果：
  - 交易态合约已按租户输出标的/标记价缺失、超过30秒或未来时间的异常合约数和最早时间，
    并落地 OPT-A001/A002 规则；健康租户隔离 MySQL 断言通过。
  - 管理端合约详情已分别展示标的价、标记价和 Greeks 快照时间。标的/标记价统一显示缺失、
    未来、新鲜或超过30秒；Greeks 按合约 `greeks_max_age_seconds` 显示新鲜/过期，值为0时明确
    显示“阈值待审批”，不把未经批准的默认秒数伪装成健康状态。旧 `snapshot_time` 只作兼容展示。
  - 合约创建、系列模板、RPC 和后台已接入 Greeks 阈值；交易态与自动上市门禁要求正数。
    数据库触发器阻止新交易态合约以0绕过，既有交易合约迁移后保留0并立即报警，必须由运营按
    `docs/templates/option-market-freshness-approval.md` 完成审批后逐合约配置。
  - OPT-A003 已按逐合约阈值检测未配置、缺失、陈旧和未来时间。当前基础风险模型不使用 Greeks，
    因此异常只阻止依赖 Greeks 的新功能并告警，不虚构对现有清算权益的影响。
  - `make gen-model` 已成功同步50张表模型，Option protobuf 和 Admin API 类型也由生成器同步；
    `20260731_zu_option_greeks_freshness.sql` 在 MySQL 8.4 连续执行两次。隔离验收确认旧交易合约
    保持0、新交易态0被拒绝、显式60秒可修复；监控确认10秒边界健康、11秒/0/未来/缺行异常。

### OPT-P0-004 修复保证金释放币种

- 状态：`VERIFYING`
- 问题：到期、强平和管理强撤部分路径使用 `fee_coin`，实物 Call 实际冻结 `margin_coin/underlying_coin`。
- 修改范围：订单冻结余额的释放只使用 `order.margin_coin`；成交后保证金批次的释放/消耗只使用
  `margin_lot.collateral_coin`。两类路径都不得用手续费币或当前合约结算币猜测历史冻结币种。
- 验收标准：
  - 实物 Call/Put 在用户撤单、IOC/FOK 撤余、到期、管理强撤、强平撤单时均使用正确币种。
  - 重放释放指令不会重复释放。
  - 不存在剩余直接用 `FeeCoin` 处理 `MarginAmount` 的代码路径。
  - 用户撤单必须在事务内锁定并重新校验订单，两个并发撤单只能有一个成功，不能把唯一键冲突暴露为SQL错误。
  - 管理强撤复用同一控制撤单状态机，并在同一事务内保存逐单、带租户/操作人/原因的不可变审计事件。
- 当前结果：
  - `OptionOrderMarginCoin` 只返回订单实际冻结的 `margin_coin`，不再以手续费币种猜测；
    资产指令和保证金批次模型在币种为空时写库前 fail-closed，实物交割/平仓释放遇到历史空值
    也明确失败，不回退结算币。
  - `20260731_zx_option_margin_coin_evidence.sql` 按合约、方向和保证金模式确定性回填历史订单及
    margin lot；只修复尚未执行的空币种资产指令，不修改处理中/成功资金历史。数据库触发器校验
    新订单/批次及历史空值修复，并保护既有非空三类证据不可变；币种按字节比较，避免数据库与
    客户端连接排序规则不同造成合法写入失败。
  - `margin_coin_invalid` 租户水位及 OPT-A032 SEV-1 规则暴露无法关联合约、币种错配或活动空币种
    指令。可确定记录自动修复；不能确定的历史记录必须按原冻结业务号与 Asset 人工核对。
  - 单元、迁移双执行、实物 Call/Put/普通订单回填、错误币种/空币种拒绝、MMP/组合保证金多触发器

### OPT-P0-005 正式到期结算价

- 状态：`VERIFYING`
- 问题：当前使用任务运行时最新单点行情，没有绑定合约到期窗口。
- 目标设计：
  - 合约配置结算源、窗口起止偏移、算法、最小样本数和价格精度。
  - 只从不可变市场快照计算，样本时间必须位于正式窗口。
  - 支持 TWAP/中位数等确定性算法、异常值过滤、版本化复核和发布。
  - 结算任务迟到也必须重放到期窗口，不能使用到期后任意价格。
- 验收标准：
  - 到期前、窗口内、到期后样本混合时只使用窗口内样本。
  - 样本不足保持等待并告警，不以 0 或任务当前价结算。
  - 相同样本可确定性重算同一结果。
  - 人工更正产生新版本和完整审批审计，旧版本不可覆盖。
  - 结算开始后使用已发布版本，不受实时行情变化影响。
- 当前监控结果：
  - 已按租户输出“到期60秒仍无已确认价格”和“已确认价格的来源、算法、窗口、样本数或
    证据集合不符合合约规则”两类水位，并分别绑定 OPT-A010/OPT-A011 规则和查询索引。
  - 隔离库精确计数及健康租户无非0泄漏纳入 OPS-010；生产通知与完整窗口/更正/结算 E2E

### 5.1 OPT-P2-001 交易日历、节假日和临时休市

- 状态：`VERIFYING`
- 设计基线：
  - 合约绑定不可变的 `trading_calendar_code`，不直接绑定可覆盖的日历行；同一代码通过更高版本、
    四眼审批和明确生效时间演进，历史版本不可修改或删除。
  - 日历使用 IANA 时区和规范化周会话。会话左闭右开，支持同日多段及跨午夜；
    任何重叠、零长度、非法星期/秒数或无可交易会话的草案都拒绝。
  - 绝对 UTC 例外窗口支持 `CLOSED`（节假日/维护）和 `OPEN`（补班/特别交易），
    同一时刻冲突时 `CLOSED` 优先。窗口及理由属于获批版本的不可变运行规则。
  - 紧急临时休市不篡改日历：创建独立 halt 记录，先暂停合约再撤销活动订单；
    解除必须引用同一 halt、填写原因并保留操作人。熔断也必须通过显式恢复接口关闭对应 halt，
    不能直接修改合约状态绕过审计。
  - 首次迁移为每个已有租户建立明确的 `CONTINUOUS_24_7` 日历并回填合约，
    只保持现有 24×7 语义，不代表生产审批完成。
- 订单准入：
  - 合约必须为 `TRADING`，且当前存在已批准、已生效、唯一的日历版本。
  - 当前时刻必须命中周会话或 `OPEN` 例外，且不得命中 `CLOSED` 例外或活动 halt。
  - 开市边界允许、闭市边界拒绝；错误时区、版本重叠或缺少日历一律 fail closed。
- 生命周期：
  - 日历只控制交易准入，不改变独立的上市、最后交易、行权截止、到期和交割时间。
  - 计划闭市保留 GTC 挂单但没有新单触发撮合；紧急 halt 必须撤销活动订单和释放资金。
  - 到期、行权、风险扫描、强平和结算不得因交易闭市停止。
- 当前实现：
  - 新增版本化日历、周会话、UTC 例外和 halt 表、模型及管理 RPC/REST；管理端已提供版本创建、
    独立复核、查询、紧急暂停和显式恢复页面，权限迁移为
    `20260731_zl_option_trading_calendar_permissions.sql`。
  - 下单在初始校验和持有合约行锁的最终准入阶段均重新解析日历；缺失、歧义、非法时区、
    闭市例外或活动 halt 一律不冻结、不入簿。未来新版本批准后，旧版本虽标为
    `SUPERSEDED`，仍在其 `effective_until` 之前参与唯一有效版本解析，切换时刻无空窗。
  - 人工暂停和标记价熔断都会先创建活动 halt 并将合约置为 `PAUSED`，再幂等撤销活动订单；
    恢复要求引用原 halt、无残余活动订单且当前存在唯一有效日历。直接
    `TRADING ↔ PAUSED` 管理修改已禁止。
  - 暂停合约到期时，生命周期任务会系统关闭 halt 并继续到期、订单处理和结算，日历不会阻断
    风险、强平、行权或清算任务。
  - 时间算法单测已覆盖纽约 DST、开闭边界、跨午夜、24×7、`OPEN/CLOSED` 优先级、
    重叠会话/例外和非法时区；Option、Admin API、App API 编译测试及管理端类型检查已通过。

  - `20260731_zk_option_trading_calendar.sql` 已在 MySQL 8.4 tmpfs 隔离实例连续执行两次；
    日历触发器非法修改和未来版本切换仍待专项执行。测试未写现有业务库，临时容器已删除。

- 运营资料：日历审批模板、年度节假日清单、临时休市/恢复记录和 T-30 天复核清单。

  - DST 切换、跨午夜、多会话、节假日、补班、开闭边界均按指定时区确定性判定。

### 5.2 OPT-P2-004 公司行动、分叉与下架调整

- 状态：`VERIFYING`；V1 代码闭环已实现，但 5001 持仓重启和预生产资产/风险验收未完成，

- 现状审计：

  - 上市后合约经济字段禁止修改，这是正确保护；但系统也没有创建后继合约并迁移存量持仓、
    空头保证金批次、可行权数量和风险快照的受控路径。
  - 现有实物交割只表达单一 `underlying_coin + settle_coin`，不能表达合并后的证券/代币篮子、
    现金替代、零碎权益、或有价值权和分叉资产。因此不能把这些事件套用单币交割。
- 设计基线：
  - 不原地修改已上市合约的行权价、合约单位、乘数、标的、到期或交割物；调整必须形成
    不可变事件、获批方案、后继合约和原/新合约谱系。
  - 事件至少记录类型、标的、公告/来源、声明日、除权日、记录日、生效日、支付日、版本和证据哈希。
    来源修订创建更高版本，不覆盖原公告。
  - 调整方案只接受精确十进制和整数分数，显式给出数量转换、权利金成本基础转换、行权价、
    乘数、合约单位、交割物及零碎差额规则；禁止二进制浮点或隐式四舍五入。
  - 创建方案即通过 P2-001 halt 暂停全部受影响合约并撤销活动订单。执行前必须证明：
    活动订单为 0、成交 outbox/inbox 收敛、资金指令收敛、无进行中行权/结算/强平，
    新后继合约已通过正常上市门禁。
  - 执行采用可重放的迁移批次和逐持仓明细。原持仓历史和成交不改写；新持仓记录来源批次，
    原持仓进入“公司行动迁出”终态。空头 margin lot、冻结业务号和剩余担保必须一一映射，
    不能通过释放再冻结制造无担保窗口。
  - 权利金成本基础守恒：
    `旧数量 × 旧开仓均价 × 旧有效乘数 =
    新数量 × 新开仓均价 × 新有效乘数 + 明示现金差额`。
    多空转换总量、单边 OI、已实现分项、费用和总收益也必须守恒。
  - 执行失败保持旧合约暂停并进入人工处理；恢复使用原批次/明细幂等键。
    回滚只能建立反向补偿方案并重新审批，不能删除或覆盖批次。
- V1 支持边界：
  - 只有权威规则明确、单一后继标的、现金结算、无篮子/零碎/或有权益、且能用现有
    `DECIMAL(32,16)` 精确表达的比例调整，才可进入自动迁移开发和验收。
  - 普通现金分红是否不调整、特别分红是否调整，必须来自目标市场产品规则，系统不自行推断。
  - 合并、收购、分拆、代币分叉、空投、现金加资产篮子、实物交割变更和缺少权威规则的下架，
    V1 一律暂停并进入人工方案，真实资金不得自动执行。
- 当前实现：
  - 新增不可覆盖的事件版本、受影响/后继合约映射、逐持仓迁移及保证金批次审计对象；
    迁移为 `20260731_zl_option_corporate_action.sql`。公司行动创建、全部源合约停牌和 halt 建立在

    `20260731_zm_option_corporate_action_permissions.sql`。
  - 自动执行只接受拆分/反向拆分、单一 `CASH` 后继合约、相同标的/币种/类型/到期和

    参考价快照和模板快照不可覆盖或删除；修订只能新建更高版本并引用 `supersedes_id`。
  - 创建时提交内嵌的 typed 合约参数模板，并通过同一个 `validateSupportedContract` 校验器；
    模板不会作为真实合约入库。参数快照写入系列证据，生成时只允许覆盖租户、合约代码、
    Call/Put、行权价、四个独立时间点和强制 `PENDING` 状态。
  - expiry 必须显式提交 UTC 秒值、周期标签、上市、行权截止、到期和交割时间，并满足现有合约
    时间门禁；节假日/DST 调整由运营先按获批交易日历形成最终时间，V1 不做隐式日期推算。
  - strike band 使用精确 `DECIMAL(32,16)` 的闭区间和步长。各 band 不重叠，边界和每个生成价
    必须能被步长精确表达；参考价只用于审批证据，不偷偷改变梯度。
  - 系列必须同时生成 Call 和 Put；每个 expiry 至少一个行权价，同一 expiry 的两侧数量和价格
    完全相同。单版本最多 500 个合约，超限、重复价格、代码碰撞或 16 位精度溢出全部拒绝。
  - 创建人与复核人必须不同。批准和生成在一个数据库事务中完成：先锁定最新版本和模板，
    重新计算完整草稿，验证全部代码无碰撞后一次性插入；任何一条失败则 0 条落库。
  - 生成合约状态强制为 `PENDING`，不得由请求覆盖。系列另有独立上市复核；未批准时生命周期
    必须保持 `PENDING`。批准后仍须在实际上市时通过交易日历和30秒内新鲜标的/标记价，
    并满足风险参数、结算规则和上市检查表；系列生成审批不等于生产上市审批。
  - 生成明细保存 `expiry_id + option_type + strike_price + contract_code + contract_id` 唯一谱系；
    重复审批或请求重放只返回原结果，不能再次创建合约。
- 首版接口：
  - 创建系列草案：内嵌合约参数模板、参考价/来源/时间/证据、显式 expiry 列表和 strike band 列表。

### 5.5 OPT-P2-007 组合/价差单原子执行

- 状态：`VERIFYING`
- 标准要求与首版边界：
  - 组合单必须作为一个订单提交，腿比例化到最简整数，成交必须保持比例和净价约束；
    禁止把多个单腿 API 顺序调用包装成“原子组合”。
  - 首版建立独立 Complex Order Book，只允许2～4条不同的期权腿、比例1～8、至少一买一卖；
    所有腿必须同租户、同用户/账户、同标的、同到期、同结算/报价币、同合约单位和乘数，
    且为现金结算、开仓、非 MMP。比例最大公约数必须为1。
  - 首版支持 `LIMIT` 休眠和 `FOK`，按父单数量乘各腿比例成交；不支持 MARKET、IOC、
    POST_ONLY、平仓腿、股票腿、跨到期/跨标的、策略拍卖或与单腿簿隐含 legging。
  - 净价定义为每份组合的 `Σ(买腿价格×比例) - Σ(卖腿价格×比例)`；
    正数为净支出、负数为净收入。每条腿价格必须满足自身 tick，组合净价必须与腿价精确相等。
  - 为避免把尚未验证的组合抵扣变成资金缺口，首版只接受逐仓卖方保证金，双方按各腿权利金、
    最大 maker/taker 费率及卖方保证金毛额预冻结，不使用跨腿组合保证金抵扣。成交同时满足
    父单净价与 taker 每腿限价：买腿不得高于其腿限价，卖腿不得低于其腿限价。
  - 首版一次准入最多与价格时间优先的一个反向父单成交。`LIMIT` 成交后余量重新休眠；
    `FOK` 要求该一个最优 maker 足量，否则0腿成交并全腿释放。跨多个 maker 聚合 FOK
    和自动连续扫簿属于后续能力。
- 原子性设计：
  - 父单、不可变腿、影子子单、资金指令和客户端幂等键同事务创建。影子子单不得进入单腿盘口、
    不得被单腿 matcher、改单、单腿撤单或公开深度消费。
  - 所有必需冻结成功后父单才进入策略簿。候选父单必须具有完全相反的规范化策略键；
    价格优先、时间优先，同用户跨账户 STP。
  - 匹配事务按父单 ID、稳定腿/影子单、用户键和合约 ID 的规范顺序锁定，重新检查交易状态、
    日历/halt、行情新鲜度、价格带、kill switch、腿限价和资金状态；用户/OI限额已在影子单
    创建时按全量腿占用，撮合前不得释放该投影敞口；随后一次性写入全部腿成交、撮合序号、
    margin lot、资产指令和 outbox。任一腿失败则整个数据库事务0腿成交。
  - 每次组合成交保存统一 `combo_match_no` 和稳定 `combo_leg_no`。资产仍通过现有幂等指令
    异步执行；同一组合成交组全部买方扣冻结成功前，任何腿的持仓事件均不可运行。之后各合约
    按原撮合序号幂等落仓，短暂水位差异由 outbox/OI 告警监控，不伪称跨合约持仓写入是一个事务。
    父单完成/撤销只按原腿冻结业务号释放未使用余额。
- 官方基线：
  - Cboe 将复杂订单定义为两个或更多不同期权系列作为一个订单提交，并保证按净价和比例执行；
    腿比例要求约分到最低项。首版策略簿与该核心语义一致。
  - Cboe 允许复杂簿与单腿簿 legging、更多腿和拍卖；这些属于明确后续能力，不能因首版有
    “组合单”名称而对外宣称已支持。参考：
    `https://www.cboe.com/document/tech-spec/document/technical-specifications/cboe-titanium-u.s.-options-complex-book-process`。
- 当前实现：

### 5.6 OPT-P2-008 RFQ、大宗与做市义务

- 状态：`DEFERRED`（有意后置，不是遗漏实现）
- 完整性判定：
  - 当前仓库没有 RFQ 请求、报价响应、接受/失效、私有参与者名单、交易报告或大宗成交对象，
    也没有对应 RPC/REST/SDK、数据库表、行情事件和运营页面。
  - 现有 MMP 只在报价组达到成交量/笔数/不利损失阈值后撤单并进入冷静期，是做市商保护机制；
    它不定义指定系列、双边报价、最小数量、最大价差、在线时间、豁免、考核或处罚，不能对外称为
    “做市义务已实现”。
  - RFQ、大宗和正式做市义务属于机构流动性与市场治理能力，不是现金结算零售标准期权的资金、
    风控、行权和结算正确性前置条件。未进入机构产品阶段时，保持无入口比实现一套未经批准的
    默认规则更安全。
- 外部基线与不能混淆的三类模式：
  - 公开 RFQ 是向批准范围内的市场参与者发出兴趣通知，响应报价可交易；是否匿名、公开给谁、
    是否展示方向/数量、响应期和交易方式必须由市场规则确定。
  - 定向 RFQ/大宗是向选定对手方询价并形成私下协商交易；大宗通常还要求合格参与者、产品资格、
    最小数量、合理价格、成交时间和限时报告，不能复用普通订单接口绕过公开订单簿。
  - 做市义务是对被委任的做市商按指定合约/系列和会话计算双边报价覆盖率、在线时间、最大价差和
    最小数量，并处理休市、熔断、行情故障、极端波动及系统故障豁免；MMP 只负责保护，二者独立。
  - 参考 CME 的
    `https://www.cmegroup.com/education/request-for-quote`、
    `https://www.cmegroup.com/clearing/trading-practices/block-trades.html`
    和 Cboe 的
    `https://www.cboe.com/us/options/trading/liquidity_providers/`。这些是设计基线，不自动成为
    本平台规则或法律结论。
- 实施前必须批准的产品/合规输入：
  1. 选择公开 RFQ、定向 RFQ、可报告大宗中的哪些模式；请求人、响应人、经纪人和管理员资格，
     KYC/AML、司法辖区、用户适当性及利益冲突规则。
  2. 单腿/组合适用范围、允许的方向和数量披露、匿名级别、接收人范围、响应/反应/接受时间、
     最少响应数、可撤回性、并发接受和信息泄漏政策。
  3. 大宗合约白名单、逐腿最小数量、最小价格变动、价格合理性区间、允许交易时间、成交报告时限、
     延迟公开、交易撤销/更正和监管报送字段。
  4. 做市商委任范围、会话/日历、双边最小数量、分价格/期限最大价差、覆盖系列比例、在线时间、
     开盘/临停/行情异常/重大事件豁免、考核周期、警告/暂停/处罚及申诉。
  5. 费用/返佣、信用和资金模型、清算对手方、成交优先权与反自成交、公平接入、数据保留期限、
     SLA、容量、监控和通知责任人。
- 获批后的首版工程边界：
  - RFQ 使用不可变请求版本和明确到期时间；报价只对授权范围可见，响应经济字段不可原地修改；
    接受时重新校验资格、日历/halt、行情新鲜度、价格带、限额和资金，只有一个报价可原子胜出。
  - 大宗成交单独建模并经双人/规则审批，不伪造成普通撮合成交；逐腿满足门槛和价格合理性，
    复用现有幂等 Asset 指令、组合成交组扣款屏障、outbox/inbox 与更正案件，不绕过清算。
  - 做市义务把批准版本、委任、豁免和每个统计窗口保存为不可变证据；原始 quote/book sequence
    可重放。MMP 触发期应从义务分母扣除还是计为违约必须由批准规则明确，代码不得猜测。
- 验收标准：
  - 无已批准机构规则时仓库没有可调用入口、数据库写路径或“支持 RFQ/大宗/做市义务”能力声明。
  - 租户、参与者和定向接收人权限隔离；未授权用户无法枚举请求、报价、对手方或成交意向。
  - 同一报价并发接受只有一笔成交；过期/撤回/不合规报价0成交、0资金动作，审计完整。
  - 大宗逐腿门槛、价格合理性和报告时限边界可重放；成交、费用、资金、持仓和 OI 守恒。
  - 做市统计能从原始序列复算，在开闭边界、halt、MMP、行情中断和豁免窗口结果唯一；
    管理员不能覆盖历史结果或自批规则。
- 当前仓库可先完成的资料：
  - `docs/templates/institutional-market-readiness.md` 已列出产品、资格、RFQ、大宗、做市义务、
    技术、运营和审批必填项；所有必需审批为空时保持 `DEFERRED`。
  - 产品运营资料和运行手册明确“无入口、不得人工撮合/补录、不得把 MMP 当义务”。
