# Option 生产运行与应急手册

## 1. 适用范围

本手册适用于 Option 合约、行情、下单撮合、资金指令、风险扫描、强平、主动行权、到期结算和实物交割的日常运行与事故处置。

管理端“期权运营工作台”是首要定位入口：先选定租户，核对异常计数和最早时间，再下钻资产指令或
对账差异。保险字段只是 Option 原始流水的代数和，兜底字段是累计平台负债，二者都不能替代
Asset 实时余额。当前表定义要求保险入金为正、出金为负，但缺口赔付写入仍为正；获批修复前，
保险字段不得解释为净变化或余额。涉及资金的关闭操作仍必须附 Asset 流水和日终对账证据。

生产值班人员不得通过直接修改业务表把失败状态改成成功。所有恢复必须使用幂等任务、管理端恢复接口或经过审批的专用脚本，并保留执行人与证据。

用户公告、到期通知、FAQ 和客服话术使用
`docs/option-product-operations-pack.md`；其中占位符和法律文本必须在发布前完成审批。

生产发布必须使用 `monitoring/option-production-readiness.env.example` 建立仓库外证明文件，并执行
`monitoring/option-production-readiness.sh`。脚本校验 55 条规则、17 项索引、日终钱包镜像和完整守恒心跳、证据哈希、功能范围、
生产监控配置和条件审批；任一失败时交易门禁保持关闭。最终签署使用
`docs/templates/option-production-readiness-signoff.md`，不得以口头确认代替不可变证据。

## 2. 角色与职责

| 角色 | 职责 |
| --- | --- |
| 一线值班 | 监控告警、初步分类、执行低风险重试、维护事件时间线 |
| Option 技术负责人 | 判断交易/清算影响、批准服务级处置、组织恢复 |
| 风控 | 决定限制开仓、暂停合约、保证金上调、强平和恢复交易 |
| 运营 | 用户通知、合约公告、行权/结算窗口协调 |
| 财务/清算 | 资产流水、保险基金、平台兜底和日终对账签字 |
| 合规 | 异常交易、价格更正、用户影响和监管留存判断 |
| 双人审批人 | 结算价更正、风险参数变更、人工资金处置 |

联系人、电话和通知群属于部署环境配置，不写入代码仓库；上线前必须在值班平台补齐并每季度验证。

## 3. 每班检查

### 3.1 开盘/连续交易

- Option RPC、数据库、Redis、消息队列和 Asset RPC 健康。
- 标的行情、标记价和 Greeks 时间戳在允许范围内。
- 风险扫描完成时间不超过两个任务周期。
- `PENDING/FAILED/MANUAL_REVIEW` 资产指令无超龄。
- outbox/inbox 无持续增长。
- 活动合约状态、交易时间、用户多/空上限、OI 上限、价格带和熔断阈值正确且均为正数。
- 最近交易控制事件无异常增长；已启用 kill switch 的用户无残留活动订单。
- 保险基金余额、平台兜底负债和限额正常。

### 3.2 到期前

- 每个合约先建立 `docs/templates/option-exercise-expiry-control-record.md`，记录四个 UTC 时间、
  自动阈值、费率、结算规则、值班人和证据目录；未完成双人复核不得进入到期窗口。
- T-24h：核对到期合约、持仓、活动订单、结算方法和行情源。
- T-2h：确认结算窗口、最小样本数、备用源和审批人员在线。
- T-30m：确认主动行权积压为 0，AUTO/DNE/相反指令版本无冲突，
  服务时钟无偏差，异常账户已经处理。
- T-5m：冻结非必要合约配置变更，检查任务水位和时钟同步。
- 到期后：确认活动订单全部进入终态，结算价已复核发布，结算批次开始。

截止时刻的控制要求：

1. 从服务时钟和独立 NTP 证据同时记录截止秒值及偏差；禁止用值班人员本地页面时间判断。
2. 截止前抽样确认只有 `TRADING/PAUSED` 合约接受新主动行权和到期指令；暂停交易不能取消
   用户行权权，`PENDING/EXPIRED/SETTLED/OFFLINE` 必须拒绝。
3. 截止后记录最新有效指令数量、AUTO/DNE/相反行权数量、被替代版本数量和拒绝计数；
   已存在的完全相同请求可幂等返回，但不能新增版本或改删历史。
4. 到期清算必须核对 `实际行权多头数量 = FIFO 分配空头数量`，以及
   `空头 gross 扣款 = 多头净入账 + 行权费`；任一差额非零按 SEV-1 处理。
5. 提前行权必须同时核对行权记录、指派、持仓数量、维持保证金、margin lot、Asset 指令和流水；
   不能因 Option 持仓已减少就推定 Asset 已成功。

### 3.3 日终

- Asset 流水与 Option bill、资产指令逐业务号核对。
- 订单成交量与买卖双方持仓变化核对。
- 权利金、手续费、行权 payoff、保险和兜底总额守恒。
- 开放对账问题为 0；非 0 必须有责任人和预计关闭时间。
- 备份和审计日志完整。

## 4. 事故级别

| 级别 | 示例 | 首次响应 | 处置原则 |
| --- | --- | --- | --- |
| SEV-1 | 重复扣款/入账、错误结算价、风险权益系统性错误、资产不守恒 | 5 分钟 | 立即停止相关交易和清算，保护证据，启动指挥 |
| SEV-2 | 风险扫描停止、行情大面积陈旧、强平/结算批量积压 | 10 分钟 | 禁止增加风险，隔离故障域，恢复关键任务 |
| SEV-3 | 单账户指令失败、单合约行情异常、管理端不可用 | 30 分钟 | 局部限制并按幂等流程恢复 |
| SEV-4 | 报表延迟、非关键指标缺失 | 4 小时 | 排期修复，不影响资金状态 |

## 5. 通用处置流程

1. 记录告警时间、租户、合约、用户、账户、业务号和最后成功水位。
2. 判断是否影响资金守恒、风险准入、价格或用户可用资产。
3. 需要时按最小范围暂停合约或禁止增加风险。
4. 保存数据库行、Asset 流水、消息、日志和配置快照。
5. 确认幂等键后执行重试；禁止修改业务号后重复调用资金接口。
6. 验证 Option 状态、Asset 流水、余额和对账状态同时恢复。
7. 恢复交易前由技术和风控双签；结算价或资金人工更正还需清算双签。
8. 关闭告警并在 24 小时内完成事件记录；SEV-1/2 在 5 个工作日内完成复盘。

### 5.1 运营指标采样异常

收到 `OptionOperationsMetricsMissing` 时，先把它视为“监控未知”，不能把其他序列消失当作恢复：

1. 从后端网络请求 `option-rpc:9105/metrics`，核对
   `wklive_option_operations_sample_success` 和
   `wklive_option_operations_last_success_timestamp_seconds`；业务端口仍为8085。
2. 查看 Option task 日志中的 `sample option operations metrics`，检查数据库连接、查询超时和任务锁；
   采样最多每15秒执行一次，最近成功时间超过45秒属于陈旧。
3. 使用运营工作台和告警目录 SQL 复核受影响租户。采样失败时 exporter 会保留最后成功序列，
   这些值只能用来定位，不能证明当前已恢复。
4. 采样恢复后确认 `sample_success=1`、最近成功时间推进；已消失异常对应的旧标签必须显式为0，
   再连续观察三个采集窗口。
5. 保存 metrics 响应、Prometheus 查询、Option 日志、数据库水位、Alertmanager 通知和确认记录。

通用规则位于 `monitoring/option-operations-alert-rules.yml`，组合策略专用规则位于
`monitoring/option-alert-rules.yml`。生产部署必须同时加载两者并配置真实接收人；仓库示例不包含
电话、群组或 webhook 凭证。

## 6. 专项场景

### 6.1 行情陈旧

触发条件：

- 标的行情、标记价或 Greeks 超过各自阈值。
- 行情时间来自未来或时间倒退。

动作：

1. 从 `OptionUnderlyingMarketStale`、`OptionMarkMarketStale` 或
   `OptionGreeksMarketInvalid` 的租户下钻交易态合约和三类独立时间戳。
2. 拒绝依赖该输入的卖方新开仓和风险降低型保证金释放。
3. 主动行权依赖的标的价陈旧时停止受理。
4. 标记价陈旧时保持上一风险状态并进入更保守限制，不能自动恢复正常。
5. 核对合约 `greeks_max_age_seconds`。0本身就是异常，不得自行套用30秒；正数必须能追溯到
   `templates/option-market-freshness-approval.md` 的产品/风控审批。快照年龄大于该值时保持
   依赖 Greeks 的功能关闭，修复发布链路后观察至少两个阈值窗口再关闭告警。
6. 检查市场消费者水位、消息积压、源服务和系统时钟。
7. 恢复后至少连续通过三个健康窗口再解除限制。

### 6.2 风险扫描超时或失败

1. 查看 `wklive_option_risk_scan_groups`、`failed_groups`、`failure_ratio` 和
   `last_completed_timestamp_seconds`；执行阶段错误另查
   `risk_scan_execution_failure_total{stage}`。
2. 将受影响账户标记为风险数据陈旧，禁止增加风险。
3. 确认其他租户/账户是否仍在刷新；不能因单点异常放弃全局扫描，也不得用存量
   `RESTRICTED` 数量代替本周期失败比例。
4. 修复行情或 Asset 依赖后重跑指定租户/账户。
5. 核对重跑前后权益、维持保证金、状态和新建强平记录；连续三个窗口失败数为0再关闭。

### 6.3 资产指令失败

1. 先检查 `OptionAssetFreezeBusinessKeyDuplicate`/OPT-A033 和
   `operations_count{category="asset_freeze_duplicate"}`。任一非0均按 SEV-1 停止该租户相关
   业务号的后续资金步骤，并按租户、`biz_type=option`、场景、业务号下钻全部冻结与流水。
2. 通过 `instruction_no` 查询 Option 指令和 Asset `biz_no` 流水。
3. Asset 已成功但 Option 未确认：优先只做对账恢复；若任务必须重放，只能使用原业务号。冻结重放会
   核对用户、钱包、币种、金额、场景、业务ID和到期时间，并接管迁移前缺少幂等行的唯一匹配冻结。
4. 同一冻结业务号查到多条冻结记录、幂等成功却没有冻结证据，或重放经济字段不一致时立即转
   SEV-1/`MANUAL_REVIEW`；不得更换业务号、删除幂等行、自动选取一条或再次冻结。重复记录只能在
   Asset、Option、清算、风控和合规共同确认用户余额、每条流水及正确经济身份后形成逐笔处置方案。
5. Asset 无流水且错误可重试：使用原 `instruction_no`/原冻结业务号重试。
6. 金额、币种、用户或方向不一致：转 `MANUAL_REVIEW`，按 SEV-1 处理。
7. 完成后核对余额镜像、冻结单剩余量、Asset 流水数量、`t_asset_idempotent` 和对账问题状态；
   OPT-A033 必须连续三个采样窗口为0且逐笔处置证据签署后才可恢复。
8. 若 `delivery_unit_id > 0`，禁止使用通用或结算指令重试；转到结算详情的实物交割单元，
   核对补资和双方资产腿后填写原因并按整个单元恢复。
9. `PROCESSING` 超过60秒时先按 `instruction_no` 查询 Asset 流水。任务会把它按原ID和指令号恢复
   为可重试状态；已存在成功流水时，重放必须幂等返回并完成对账，不得另建指令或手工补资金。
10. 恢复前确认所有较高step均无成功和流水；恢复后确认原流水仍恰好1条、`retry_count`没有因
    stale恢复被人为增加、全部指令已对账且批次终态。生产演练还必须保存执行者实例、claim时间、
    停止时间、恢复任务实例和OPT-A006通知/恢复记录。

### 6.4 风险强平积压

1. 立即禁止受影响账户增加风险。
2. 核对标记价来源、权益和维持保证金，避免基于错误行情扩大处置。
3. 检查撤单、保证金消耗、保险和平台兜底各步骤。
4. 逐个 `liquidation_no` 幂等恢复；不得批量跳过失败步骤。
5. 核对接管持仓、用户持仓、保证金批次和 Asset 流水总额。

### 6.5 主动行权积压

1. 到期任务必须等待未完成主动行权，避免重复清算。
2. 核对长仓冻结数量、指派总量、空头可用量和所有资产指令。
3. 不得取消未被实际指派用户的平仓单。
4. 到期临近仍未恢复时，由风控和运营决定暂停主动行权入口并公告。
5. 截止后不得通过改表补录 DNE/相反指令；只能查询或幂等重放截止前已存在的同一请求。
6. 到期应核对实际行权多头数量与 FIFO 空头承担数量相等，DNE/阈值以下数量不得产生 payoff。

### 6.6 结算价无法生成

1. `OptionSettlementPriceOverdue` 触发时保持合约在等待结算状态，不使用 0 价或任务当前价替代。
2. 核对正式窗口内不可变样本数量、来源健康和异常值。
3. 主源失败时只按产品规则中已批准的备用源切换。
4. 人工价格必须经过计算人、复核人双签，并生成新版本和理由。
5. `OptionSettlementPriceInvalid` 按 SEV-1 阻止结算；核对已确认版本的来源、算法、窗口边界、
   最小样本数、证据 JSON、每个不可变快照 ID、复算中位数和四眼身份。自动版本必须为
   `authoritative-market/MEDIAN`；人工更正必须为 `manual-correction/MANUAL`。
6. 禁止原地修正或删除任何版本。自动候选被拒绝且证据未变化时不会自动重建；需要更正时由
   独立人员创建、复核追加版本，或等待确有新增的正式窗口证据。
7. 发布后保存输入样本、算法版本、输出、审批和公告。

### 6.7 结算批次部分失败

1. 禁止把批次直接改为 `DONE`。
2. 按 `settlement_no + step_no` 核对所有扣款步骤。
3. 全部前置扣款成功前不得执行对应入账。
4. 对失败指令按原业务号重试；已成功指令只核对不重发。
5. 完成后验证多头收入、费用、空头扣款、保险/兜底和交割资产守恒。
6. 现金结算的最小验收基线：正式价格版本与批次绑定；`total_credit=total_debit`；每条 Asset
   指令为成功且对账完成；相关钱包 `期末总额=期初总额`（不含明确外部费用/注资），冻结归零；
   结算、批次和合约均进入终态。再次运行生命周期和资产任务，不得增加结算、指令或流水。
7. 缺少已确认正式价时，合约必须保持等待且结算数为0；禁止通过改状态、填0或使用最新价绕过。
8. 扣款 RPC 失败时先保存失败指令的 `instruction_no`、`retry_count`、错误码和 Asset 查询结果；
   较高 step 必须保持未成功且无流水。不得换业务号重建指令，也不得手工给买方入账。
9. 依赖恢复后用原指令号重试。若失败发生点不确定，先按原指令号查询 Asset 流水：已存在则
   进入对账/完成路径，不存在才执行扣款。关闭事件前确认原扣款流水恰好1条、所有 step 已对账、
   批次终态、逐币守恒且冻结归零。
10. 余额不足连续失败达到20次时必须进入 `MANUAL_REVIEW` 并停止自动重试；保存原状态、
    `retry_count=20`、最后错误、余额、冻结、已有流水和后续 step 为0的屏障证据。不得通过 SQL
    清零次数、临时给买方入账或改用新结算指令。
11. 补资前使用 `docs/templates/cash-settlement-topup-recovery-approval.md`。至少由清算确认应付金额和
    原指令，由财务确认资金来源、币种、金额及独立补资业务号；生产批准人与执行管理员不得为空。
12. 补资必须通过 Asset 的正常入账入口并使用独立、可追溯的业务号；补资流水只能有一条。
    补资不是结算完成，也不得把补资业务号用作原扣款业务号。
13. 管理端人工重试必须使用原 `instruction_id/instruction_no`，填写1至64字符的机器可检索原因并
    携带已认证管理员身份。缺原因、超长原因或缺操作人均应拒绝，且指令仍为
    `MANUAL_REVIEW/retry_count=20`、不生成审计事件。
14. 合法恢复把指令重置为待执行，并在同一数据库事务追加
    `ASSET_INSTRUCTION_MANUAL_RETRY` 事件；事件必须包含操作人、用户、合约、原因、原状态、
    原重试次数和原错误。事件写入失败时重置必须回滚；事件禁止 UPDATE/DELETE。
15. 恢复后先确认原扣款流水恰好一条并已对账，再允许较高 step；最终核对补资后的逐币守恒、
    冻结0、3条结算指令全部成功对账、结算/批次/合约终态和审计事件仍可查。

### 6.8 保险不足或平台兜底超限

1. 停止新增裸卖风险或提高保证金，不得继续无限形成平台负债。
2. 核对保险覆盖调用和已用额度。
3. 由风控、财务和管理层决定补足、减仓或暂停产品。
4. 任何人工注资或负债调整必须有独立业务号和财务凭证。

### 6.9 用户 kill switch

1. `OptionKillSwitchActiveOrders` 或
   `operations_count{category="kill_switch_active_orders"}` 非0时，先在控制事件/订单表定位
   具体用户；Prometheus 只保留租户和受影响用户数。
2. 用户启用后，新单必须立即返回 `USER_KILL_SWITCH`；启用接口返回前应完成
   `FUNDING/PENDING/PART_FILLED` 活动订单的撤销或进入资金释放流程。
3. 若撤单失败，kill switch 必须保持开启；使用原订单和原资金业务号重试，不得先解除开关。
4. 核对平仓冻结数量、保证金币种、释放指令和 Asset 流水；确认活动订单查询为 0。
5. 只有管理员可解除。解除前必须记录用户确认、失败原因已消除、资金对账和解除理由。
6. 从 `t_option_trading_control_event` 保存启用/解除操作人、时间、理由和失败恢复证据。

### 6.10 价格带或熔断

1. `OptionTradingControlNotConfigured`、`OptionPriceBandRejectionBurst`、
   `OptionCircuitBreakerTriggered`、`OptionPausedContractActiveOrders` 或
   `OptionPositionLimitRejectionBurst` 触发时，按租户下钻控制事件和合约；指标中的 count
   是事件数或超阈值对象组数，不是用户资产金额。
2. 价格带分母固定为窗口内 `ORDER_CONTROL_EVALUATED/TRADING_CONTROL`，分子固定为
   `ORDER_REJECTED/ORDER_PRICE_BAND`。10%边界不触发，必须严格超过10%或拒单超过20笔才触发；
   发布后首个一分钟窗口若只有旧版拒单而没有分母，仅保留绝对笔数门禁。
3. 下钻时按租户、合约和最近60秒分别统计上述两类不可变事件，保存请求数、拒绝数和
   `rejected_count/request_count`；指标 count 是超阈值合约数，不能当作拒单率。
4. 大量 `ORDER_PRICE_BAND` 拒单时，先核对标记价数值及 `mark_snapshot_time`，不得临时扩大价格带掩盖陈旧行情。
5. `CIRCUIT_BREAKER` 触发后合约应为 `PAUSED`；检查所有活动订单在 30 秒内终止或进入释放流程。
6. 保存触发前标记价、当前标记价、跳变比例、阈值、行情来源和控制事件。
7. 判断为错误行情时，修复行情源并连续观察三个健康窗口；判断为真实波动时，由风控决定延长停牌或调整参数。
8. 恢复交易必须由风控和技术双签，通过合约状态更新接口执行并留下审计；不得直接改表。

### 6.11 自成交保护异常

1. `OptionSTPBurst` 触发时从 `stp_user_breach/stp_tenant_breach` 判断阈值层级，
   再按租户从不可变控制事件定位用户；不得把 UID 加入 Prometheus 标签。
2. STP 固定采用 cancel-taker，按用户生效，不能通过不同 `account_id` 绕过。
3. 核对被取消 taker 没有成交、资金流水或持仓变化，原 maker 仍保持原状态。
4. 高频触发时保存用户、合约、订单和客户端来源，转风控/合规判断是否为程序错误或操纵行为。
5. 不得关闭 STP 来恢复用户交易；应由用户修复策略并撤销冲突报价。

### 6.12 疑似错单或异常成交

1. `OptionTradeCorrectionException` 任意触发均按 SEV-1；它覆盖待复核案件、执行超60秒和
   `MANUAL_REVIEW`，先从案件工作台定位具体合约和用户。
2. 保存订单簿、行情快照、匹配顺序、双方订单、持仓、Asset 流水和全部日志，
   将只读证据包地址填写到 `evidence_ref`。
3. 在后台创建异常成交现金更正草案。创建事务会把合约切为 `PAUSED` 并留审计，
   随后撤销活动订单；若批量撤单部分失败，使用合约强撤入口继续，不得先恢复交易。
4. 原成交不删除、不改价、不改数量。现金更正分录仅允许原成交双方、手续费账户或
   保险账户，币种必须等于原成交币种，每币种借贷总额必须精确相等。
5. 申请人不得复核自己的案件。复核人逐项核对证据、账户、币种、金额和用户通知方案；
   拒绝也必须填写原因，且不会自动恢复合约。
6. 批准后系统把全部扣款作为 step 1、全部入账作为 step 2。任何扣款未成功时入账
   不得运行；使用原 `instruction_no` 重试，达到阈值转 `MANUAL_REVIEW`。
7. 完成态必须同时满足：全部资金指令成功并对账、借贷净额为 0、案件为 `COMPLETED`、
   受影响用户已通知、控制事件与证据完整。
8. 恢复交易不由案件自动执行。技术和风控双签后，通过合约状态接口恢复并再次检查
   正数限额、价格带、熔断阈值和最新行情。

### 6.13 MMP 触发、撤单失败或误恢复

1. `OptionMMPException` 或 `operations_count{category="mmp_exception"}` 非0时，先按租户
   从 MMP 工作台下钻 `user_id/contract_id/group_code`；指标值是异常组数。
2. 再核对配置、状态、窗口开始、累计量、
   笔数、累计不利损失、触发原因、冷静期和 `last_error_msg`。
3. 从控制事件保存触发成交、成交前标记价、成交价、maker 方向、手续费、三个阈值及
   组级撤单结果；不得用成交后的标记价重算并覆盖原证据。
4. `TRIGGERED` 或配置变更暂存 `DISABLED` 时，新 MMP 报价必须持续拒绝。查询该组
   `FUNDING/PENDING/PART_FILLED` 活动单；非 0 时按原订单和原资金业务号幂等撤销。
5. 撤单或资金释放失败时保持触发/禁用，不得先人工恢复。Asset 已成功但 Option 未确认时
   只做状态对账，禁止生成新释放业务号。
6. 自动恢复仅允许冷静期截止后的首笔新 MMP 单原子清空窗口。人工恢复必须在管理端填写
   复核理由，系统再次清残单后才转 `ACTIVE`；活动/禁用组的“恢复”请求应被拒绝。
7. 若判断阈值不适当，走配置变更而非直接改表。变更过程会先禁用并清理旧报价，
   成功后才激活；保存风控审批、旧/新参数和撤单清单。
8. 恢复后连续观察三个窗口，确认同组残单为 0（恢复后新单除外）、非 MMP/其他组未被误撤、
   资金释放已对账、控制事件完整，再关闭事件。

### 6.14 组合保证金参数缺失、变更或回滚

1. `OptionPortfolioRiskConfigMissing`、`OptionPortfolioRiskVersionMismatch`、出现“无有效组合
   风险配置”或账户 `RESTRICTED` 时，先按 `tenant_id + settle_coin`
   查询版本状态、有效期和最近审批；不得临时恢复内置默认参数或直接改风险账户状态。
2. 核对风险账户记录的配置 ID/版本、算法、情景损失、裸空头底线、集中度附加和流动性附加；
   同时抽查组合保证金卖单的 `portfolio_risk_config_id/version`。新单必须为正且对应订单
   `create_times` 唯一有效版本，普通单应为 `0/0`。迁移前历史单允许 `0/0`，只能标记为
   “历史准入证据不可用”，不得人工猜测回填。下单与定时扫描在同一时点解析版本不一致时，
   按 SEV-1 模型计算错误处理。
3. 新参数先创建 `PENDING` 草案，附变更原因及回测/验证证据引用；创建人不得审批。
   批准未来版本后，核对旧版本截止时间精确等于新版本生效时间。
4. 参数异常时不修改历史版本。选择最近一次已验证版本创建“回滚版本”，填写新的原因、
   证据和生效时间，再由独立管理员审批；回滚仍是更高版本。
5. 回滚生效前保持组合卖方新增风险关闭；必要时暂停相关合约。生效后重跑风险扫描，
   核对至少一个有价差、一个裸空头和一个跨期限账户的确定性复算结果。
6. 保存版本前后风险账户快照、订单准入配置 ID/版本、告警、审批人、回测报告、独立验证签字
   和恢复时间。不得通过改单或 SQL 改写已经落单的配置证据。
   连续三个扫描周期一致且无开放 SEV-1/2 问题后才恢复组合保证金准入。

### 6.15 实物交割补资与违约人工复核

1. 按 `tenant_id + delivery_unit_no` 定位交割单元，核对批次、合约、多空双方、数量、
   交割币/数量、支付币/金额、补资截止和全部资产指令；不得只按整批状态判断个别用户结果。
2. 执行顺序必须是多头应交资产扣减、空头已冻结担保扣减、双方入账。任一前置扣款未成功并
   对账时，相关单元的所有入账指令必须保持不可运行；其他单元可以继续。
3. `CURE_REQUIRED` 时按已批准通知渠道提示用户在 `cure_deadline` 前补足资产。
   自动任务只用原 `instruction_no` 重试，不得创建替代扣款或临时转入平台资金。
4. 截止后仍失败转 `DEFAULTED/MANUAL_REVIEW` 并停止自动重试。保存 Asset 返回、
   余额与流水、重试次数、首次失败/截止时间、用户通知回执和单元内已成功的资产腿。
5. 用户补资且清算确认后，可从管理端重试原失败指令。若已有扣款成功，先确认该资金仍处于
   待交割清算状态；禁止对成功腿再次扣款或手工把状态改成成功。
6. 当前安全基线不提供自动退款、自动放弃、罚金、拍卖或平台承接。需要这些经济处置时，
   必须由产品、风控、清算和法务审批新的规则与会计分录后另行发布；事故现场不得临时决定。
7. 关闭条件：单元全部指令成功且对账、单元为 `COMPLETED`、批次计数正确、双方通知完成、
   日终两币种资产守恒、事件和人工操作证据完整。

### 6.16 公司行动停牌、迁移失败和人工处理

1. `OptionCorporateActionDue` 表示生效后仍处于批准/执行中，
   `OptionCorporateActionException` 表示人工/失败、失败持仓、映射或源/后继合约门禁异常；
   两者均先保持源合约停牌、后继合约禁止上市，再从后台事件和映射下钻。
2. 收到权威公告后先保存原文件、URL/文号和内容哈希，按
   `docs/templates/corporate-action-case.md` 填写事件、目标市场规则、关键日期和影响合约；
   不得从行情变化自行推导拆分、分红或合并规则。
3. 后继合约必须先按普通合约流程创建为 `PENDING`。登记公司行动时，源合约停牌和 halt
   在同一事务完成；随后检查活动订单、撤单资金释放和 halt 的 `last_error_msg`。任一残单或
   失败存在时不得复核通过。
4. 创建人不得复核。复核人核对官方证据哈希、整数分数、原/新有效乘数、数量步长、到期和
   结算类型。只有拆分/反向拆分、单一现金后继和精确换算可选 `AUTO`；其他事件必须
   `MANUAL`，并保持源合约停牌。
5. 到达生效时间后监控每个映射的 `position_completed/position_total`、稳定持仓游标和错误。
   执行门禁非 0 时先处理原订单、outbox/inbox、资产指令、行权、强平、结算或实物单元，
   不得删记录或改状态绕过。
6. 自动迁移使用原 action/mapping/position 幂等键和每批 100 条续跑。单笔事务同时建立后继
   持仓、标记原持仓迁出、失效旧行权指令并重指向 margin lot；禁止释放后重新冻结保证金。
7. 失败三次或进入人工态时按 SEV-1 建案。核对已完成逐持仓明细，禁止删除或回滚已完成批次；
   修正经济参数只能发布更高事件版本或经重新审批的补偿方案。
8. 关闭前必须证明：全部映射完成、旧合约 `OFFLINE`、后继合约仅在日历与行情门禁通过后上市、
   首次风险扫描正常、相关钱包解除 `RESTRICTED`、成本基数和逐币保证金/Asset 冻结差额为 0，
   并完成用户、做市商、客服、清算、风控和合规通知。

### 6.17 合约系列创建、复核和批量草稿异常

1. `OptionContractSeriesReviewStale` 表示待复核超过24小时；确认是否仍有业务有效性，
   不再需要的版本也必须通过正常拒绝流程留痕。`OptionContractSeriesInvariantIssue` 任意触发
   均按 SEV-1 冻结整系列上市，不能手工补行或改计数。
2. 使用 `docs/templates/contract-series-approval.md` 收集目标市场规则、参考价原始证据、显式
   expiry、strike band 和参数模板。系统不会从“每周五”或行情自行推导节假日顺延和价格梯度。
3. 创建前核对 request key 只用于这一份规范化输入。同 key 同内容可安全重试；同 key 不同内容
   必须拒绝。修订使用新 request key 并形成更高 `series_code + version`。
4. 创建人不得复核。批准前核对预计数量不超过500、每个 expiry/strike 固定一对 Call/Put、
   代码命名不碰撞、UTC 时间仍在未来、模板风控/费用/结算参数完整。
5. 批准在单一事务生成合约和谱系；任一冲突或校验错误必须保持0条新增。不得人工补插缺失
   Call/Put、删除错误明细或把系列状态改成已生成。
6. 成功后核对 `generated_contract_count = expected_contract_count = detail count`，谱系中每个
   `contract_id` 存在且状态为 `PENDING`。不一致立即按 OPT-A028 升级并冻结整个系列上市。
7. 系列批准不等于上市。对每个合约执行普通上市检查、行情/做市准备和审批；在任何合约失败时
   保持其 `PENDING`，不要为了保持“整齐”而绕过门禁。
   单合约后台也只能创建 `PENDING` 且不能人工改状态；若生命周期持续不上市，依次核对用户多空/OI
   限额、价格带、熔断、标的/标记价及各自快照时间、交易日历和系列上市复核，不得直接改表。
8. 关闭条件：请求/审批/证据和 payload hash 已归档，数量/Call-Put/谱系核对一致，
   所有拟上市合约分别签署上市检查表，未上市合约仍保持 `PENDING`。

### 6.18 期权链、公开盘口、24h 统计和 OI 异常

1. `OptionPublicChainPairIssue` 表示交易态同一标的/到期/行权价不是恰好一 Call 一 Put；
   `OptionOpenInterestImbalance` 表示 HOLDING 多空事实不平衡。先按租户下钻，不能用另一租户、
   缓存或前端结果修补数据库事实。
2. 使用 `docs/templates/public-market-readiness.md` 固化字段、缓存、限流、SLA 和降级文案。
   未批准前不得让 CDN 长缓存或向外承诺流式 L2 深度。
3. 链缺腿时先核对同租户、标的、精确到期、行权价、状态和系列谱系；不得复制另一腿行情、
   临时改状态或在前端隐藏问题。未上市合约本就不应出现在公开链。
4. 盘口异常时直接按订单表核对 `PENDING/PART_FILLED` 正余量；`FUNDING` 未入簿，
   撤单/完成/过期和零余量不应计入。不得用 Market 标的深度填补 Option 深度。
5. 24h 统计按服务端 Unix 秒和成交时间重算。确认边界、时钟和每笔成交只计一次；
   不按买卖双方双计，也不使用订单委托量代替成交量。
6. OI 同时核对 `HOLDING` 多头和空头。正常必须相等；不等时以较大侧保守展示并触发
   OPT-A029，排查持仓 outbox/inbox、资产指令和持仓事件，不手工把较小侧补平。
7. 缓存/CDN 若存在，必须保留 `generated_at`、三类行情快照时间、持仓水位和来源字段；
   超过批准 TTL 时显示延迟/不可用，不继续展示成实时数据。
8. 关闭条件：链和谱系一致、盘口与活动订单抽样一致、24h 统计精确一致、多空 OI 相等，
   连续三个窗口达到 SLA，且缓存清理、用户影响和客服通知证据已归档。

### 6.19 组合/价差单冻结、残腿和人工处理

1. 先在“期权运营工作台 → 组合父单”按租户和 `combo_no/id` 查询，使用下钻查看父单、不可变腿、
   带父腿关联的影子子单、每腿 `-FREEZE`/释放指令和 `combo_match_no` 成交。页面最多展示成交和
   指令各100条并同时显示总数；出现截断提示时继续按业务号执行本节 SQL/日志核对，不得把前100条
   当作全集。概览中的“组合父单超龄/人工态”与“组合结构/成交组异常”任一非0都按 OPT-A030
   处理；组合超龄阈值默认60秒且只允许10至300秒。禁止只撤、重试或改动一条影子子单。
   同时查看 `monitoring/option-alert-rules.yml` 对应的四项 Prometheus 指标；监控抓取地址为
   后端网络内 `option-rpc:9105/metrics`，不允许将该端口直接发布到公网。
2. `FUNDING` 超过60秒时逐腿核对冻结指令。任一腿非 `SUCCESS` 时0腿应处于
   `PENDING/PART_FILLED/FILLED`；若已有策略成交立即按 SEV-1 建案。重试必须保留原
   `instruction_no` 和 `target_biz_no`。
3. `ACTIVE/PART_FILLED` 异常时核对父数量与每腿 `qty=父qty×ratio`、
   `filled=父filled×ratio`、`unfilled=父unfilled×ratio`，并确认影子单不在普通盘口。
   不得通过修改一条腿的价格、数量、方向、比例、合约或进度“修平”。
4. 一次成交用 `combo_match_no` 聚合。全部腿交易、Asset 指令和 outbox 必须同时存在；
   腿号连续且与父腿一致。任一买方 `DEDUCT_FROZEN` 未成功时，该组所有持仓事件都应不可运行。
   `OptionComboDebitBarrierViolation` 表示 SQL 调度屏障被绕过后事务二次校验仍发现异常，按
   SEV-1 处理；`OptionComboDebitBarrierStale` 连续2分钟表示超龄屏障，按 SEV-2 处理。
5. `CANCELING` 超过60秒时按每条影子单原冻结业务号核对释放；已成功腿不得换业务号再释放。
   全部影子单终态后父单应自动为 `CANCELED`。任一资产指令20次失败会把父单转
   `MANUAL_REVIEW`，按资金类 SEV-1 流程处理。
6. halt、kill switch、到期或管理员强撤命中影子单时，系统会解析到父单并全腿撤销。
   若只看到一腿状态变化或普通盘口包含 `combo_order_id>0`，立即暂停相关合约和组合入口。
   管理员强撤只能使用工作台“整组强撤”，必须填写原因；不要调用普通单撤销或直接改状态。
   注意：活动影子单本身是正常策略簿记录，不能仅凭表中存在 `combo_order_id>0` 判断普通簿污染；
   必须结合普通盘口响应、matcher 运行时指标或查询链路证据。
   `OptionComboSimpleBookIsolationViolation` 任意一次即按 SEV-1：系统已拒绝污染响应/撮合，
   但仍须立即暂停相关入口并保存指标标签、日志、父单和盘口抽样。
7. 首版 FOK 只接受一个最优 maker 足量，不跨 maker 聚合；LIMIT 与一个 maker 成交后余量休眠。
   这属于批准的产品边界，不得向用户宣传为 legging、拍卖或多 maker FOK。
8. 关闭条件：父/腿/影子数量一致，所有组合成交组腿数完整，资金指令和对账成功，
   outbox/inbox 最终成功，Asset 净额守恒，普通盘口污染为0，并归档 COMBO 场景、告警和用户通知。
   告警关闭还必须连续三个采集窗口为0，并保存 Prometheus 查询、Alertmanager 通知和确认记录。

### 6.20 RFQ、大宗与做市义务请求

1. 当前能力状态为 `DEFERRED`，没有生产 RFQ、大宗成交或做市义务入口。收到销售、客户、经纪人、
   做市商或管理员请求时，只能登记产品需求并引用
   `docs/templates/institutional-market-readiness.md`，不得人工代撮合或直接补成交。
2. 现有 MMP 是报价组风险保护，不是做市义务考核。不得根据 MMP 是否启用、触发次数或冷静期
   推断做市商已经满足/违反双边报价、最小数量、最大价差、覆盖率或在线时间义务。
3. 不得用普通用户限价单、组合单、异常成交更正、数据库插入或 Asset 手工流水模拟 RFQ/大宗；
   这些路径缺少参与者资格、信息隔离、价格合理性、交易报告和监管审计语义。
4. 外部客户声称已与对手方达成交易时，客服只记录双方提供的时间、合约/策略、方向、数量、价格、
   对手方、沟通渠道和证据地址，立即转合规/市场运营；不得承诺平台确认、清算或补录。
5. 产品进入立项时，产品、合规、法务、风控、市场运营、清算和技术先共同签署准备模板，再建立
   数据模型和接口。任何“先上线再补规则”的例外都应拒绝。
6. 关闭条件：未立项请求已有书面拒绝/后置答复和客户通知；已立项请求具备完整规则版本、责任人、
   验收计划和变更审批，在正式实现、预生产验收及上线批准前仍无生产入口。

### 6.21 管理员受治理字段越权修改

1. `OptionAdminEconomicMutationRejected` 任意触发进入 SEV-3 安全审计；
   `OptionAdminEconomicMutationBurst` 表示同一有限标签组五分钟超过3次，升 SEV-2。
2. 按 `tenant_scope/object_type/reason` 定位结构化应用日志，再核对租户、合约、管理员、请求来源、
   网关请求 ID、变更工单和当时对象版本。Prometheus 标签不含管理员/合约 ID，不能只靠指标定位。
3. `status_bypass` 表示试图绕过 lifecycle/halt/resume，`series_economics` 表示修改系列治理合约，
   `listed_economics` 表示修改已上市合约经济字段。请求被拒绝不代表凭证和调用来源可信。
4. 禁止为“消除告警”临时开放更新或直接改表。合法变更必须走对应追加版本、四眼审批、公司行动、
   合约系列修订或受控 halt/resume 流程。
5. 应用 Counter 只覆盖经过 Option Admin RPC 的拒绝。直接 SQL 被触发器拒绝时，触发器内审计写入
   会随失败事务回滚，必须从 MySQL audit/general log、堡垒机或等价数据库安全平台取证。
6. 关闭条件：确认没有数据变化；凭证、来源和工单已核实；必要时吊销会话/密钥；数据库审计无
   旁路成功；连续三个窗口无新增并归档安全结论。

### 6.22 日终资金守恒差额

1. 每个业务日按 `docs/templates/option-daily-fund-reconciliation.md` 使用同一 Asset 一致性
   快照和 Option 截止点，逐租户、逐币、逐用户钱包/平台账户范围复算。未完成快照只能标记
   `INCOMPLETE`，不得用缺数据算出0。
2. 非零差额以稳定键 `DAILY:{business_date}:{dimension_type}:{dimension_key}:2` 写入
   `t_option_reconciliation_issue(check_type=3,status=OPEN)`；
   `OptionDailyConservationMismatch` 任意触发按 SEV-1，暂停次日相关产品开放。
3. 核对期初/期末总额、外部转入转出、Option 业务入扣、人工调整，以及
   `FEE_REVENUE/INSURANCE_FUND/OPTION_BACKSTOP` 三类平台账户。
   Option 保险流水和兜底负债只是交叉证据，不是 Asset 余额。
4. 重跑必须使用同一键并累计发现次数。禁止换业务日期、币种或 scope 生成新键来隐藏旧问题；
   差额为0后保留原记录并转 `RESOLVED`，不以 `IGNORED` 代替财务解释。
5. 当前仓库已实现 scope=1 钱包镜像及 scope=2 完整守恒自动任务。Scope 2 在同一 MySQL
   REPEATABLE READ 事务中复算用户钱包、平台账户和 Option 指令/bill 子账，追加不可变运行/明细、
   稳定问题单和零差额成功心跳；任何未知分类、链断裂或关联不完整均失败关闭。仓库闭环通过不代表
   生产关闭条件，仍须用真实 Asset 流水完成调度、容量、通知送达和四方签署。
6. 关闭条件：技术、清算、财务、合规四方签署；逐币差额为0；所有补偿使用受控业务号；
   原问题已恢复；次日开放审批和全部证据归档。

### 6.23 日终钱包镜像核对失败或缺失

1. `option.ProcessDailyReconciliation` 每小时由 System 触发，但自动任务只在 UTC 00 点窗口执行，
   快照归属前一 UTC 业务日；该日已有 scope=1 成功 attempt 时跳过。最近一次有差异、执行失败
   或36小时无成功分别触发 OPT-A031 SEV-1。
2. 先查 `t_option_reconciliation_run` 的最新 attempt 和 `detail`，再从
   `t_option_reconciliation_issue(issue_key LIKE 'ACCOUNT_MIRROR:%')` 按币种下钻。运行行不可修改
   或删除；禁止直接改表制造成功心跳。
3. 核对 Asset `wallet_type=5` 与 `t_option_account` 的用户/币种覆盖、总额、可用、冻结和锁定；
   Option 只允许钱包镜像 `account_id=0`，遗留非0账户也会判差异。不要把多个账户相加后抵消。
4. 调度失败时检查 System cron、Kafka `option-tasks` 消费、MySQL 与 Redis 任务锁。显式 tenant
   手工触发可在 UTC 00 点窗口外为前一业务日追加 attempt；不得覆盖旧 attempt 或更换日期隐藏失败。
5. 差异修复必须通过 Asset 正式资金/镜像同步路径，并保留业务号和 Asset 流水；不得直接改
   `t_option_account`。健康重跑会把旧 `ACCOUNT_MIRROR` 案件转为 `RESOLVED`。
6. 关闭条件：最新 attempt 为成功、36小时缺失告警恢复、全部镜像案件已恢复、连续三个采样窗口
   正常并归档运行 ID。该关闭条件不自动关闭 6.22 的 scope=2 完整资金守恒。

### 6.24 保证金币种证据异常

1. `OptionMarginCoinEvidenceInvalid` 触发后立即停止相关租户的订单释放、margin lot 消耗和资产指令
   人工重试。不得把 `fee_coin`、结算币或页面显示币种当作实际冻结币种。
2. 按订单号/`target_biz_no` 查询 Asset 原冻结流水，再核对订单 `margin_coin`、margin lot
   `collateral_coin`、资产指令 `coin` 和合约当时版本。实物 Call 卖出全额担保应为标的币，
   实物 Put、买方权利金及现金结算保证金通常为结算币，但结论必须由原冻结流水证明。
3. 迁移会自动修复能够由租户+合约确定的历史订单/批次，以及尚未执行的空币种指令；不会修改
   `PROCESSING/DONE` 资金历史。仍异常的记录表示合约关联或原始证据不足，必须创建 SEV-1 事件。
4. 禁止直接改写非空币种证据。若历史空值需修复，保存 Asset 流水、合约快照、双人复核和 SQL
   影响范围，只允许填入已证明币种；已经成功但证据不一致时走对账/更正流程，不重放原指令。
5. 关闭条件：异常水位连续三个周期为0，相关冻结/释放流水精确对账，未产生重复释放；事件记录
   包含受影响订单、批次、指令、币种、金额、迁移输出、复核人与恢复时间。

## 7. 恢复验证

恢复不是“任务返回成功”，必须同时满足：

- 订单、持仓、行权、结算或强平状态符合状态机。
- 每个资金动作存在唯一 Asset 流水，金额、币种、方向和用户一致。
- 资产指令为成功且对账状态为已确认。
- 无新增开放对账问题。
- 风险扫描时间和行情时间恢复。
- 监控连续三个窗口正常。
- 技术与业务责任人记录恢复结论。

## 8. 禁止操作

- 直接把失败指令、行权、结算或强平状态更新成成功。
- 删除或修改已经发布的结算价记录。
- 为绕过幂等冲突修改业务号后重发同一资金动作。
- 在来源不明时手工刷新行情时间戳。
- 在未核对 Asset 流水时重复扣款或入账。
- 使用生产用户资金临时填补保险或平台账户。
- 直接更新 kill switch、控制事件或合约状态绕过管理员接口和审计。
- 通过扩大价格带或把熔断阈值设为 0 恢复交易。
- 删除原异常成交、修改现金更正分录，或用反向下单伪造成交撤销。
- 直接更新 MMP 状态/计数、清空 `last_error_msg`，或在组内残单和资金释放未完成时恢复。
- 直接修改、删除、重新激活组合保证金历史参数，或在缺少有效批准版本时启用默认参数。
- 跨过实物交割单元步骤屏障入账、为失败单元更换业务号、直接修改交割单元经济字段，
  或在未获批准时自动退款、没收、垫资、拍卖和放弃行权。
- 直接修改公司行动证据、换算参数、迁移明细或原持仓历史；在迁移未完成时恢复源合约或提前
  上市后继合约；对复杂篮子、分叉、空投、实物变更或未知下架规则启用自动路径。
- 直接修改/删除系列、expiry、strike band 或生成谱系；人工补插半套 Call/Put；复用 request key
  提交不同参数；把“系列已生成”当作上市批准，或批量把生成合约直接切换为 `TRADING`。
- 单独撤销、改单或撮合组合影子子单；修改父单/腿经济字段或执行进度；把组合单拆成多次单腿下单
  冒充原子成交；在任一腿扣冻结未完成时人工推进持仓事件；更换组合腿冻结/释放业务号重试。
- 使用普通单、组合单、MMP、异常成交更正、SQL 补录或 Asset 手工流水冒充 RFQ/大宗成交；
  在未批准机构规则时创建隐藏入口，或把 MMP 报价保护结果解释为做市义务考核。
