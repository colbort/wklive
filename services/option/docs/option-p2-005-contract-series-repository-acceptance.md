# OPT-P2-005 合约系列仓库级验收记录

## 1. 结论

截至 2026-08-02，标准到期序列与行权价系列 V1 已完成仓库级 MySQL 8.4、独立 Redis 和真实
Asset gRPC 总门禁验收。20 路相同请求并发创建只形成一个系列版本；两名复核人并发批准只原子
生成一批 500 个 `PENDING` 合约，包含 2 个显式 expiry、125 个精确行权价、250 Call 和
250 Put。审批响应丢失重放不重复生成；任一代码冲突整批回滚；502 条输入在写库前拒绝。

系列生成不等于允许交易。独立上市复核前延迟消息保持 `PENDING`；批准后缺行情、行情超过30秒、
消息 due identity 不匹配时仍保持 `PENDING`，只有日历与全部运行时门禁同时满足时才允许一个合约
进入 `TRADING`。延迟队列与周期扫描现在共用同一个事务门禁，不再存在直接改状态的旁路。

本结论不等于批准生产批量上币。目标市场的年度到期日、节假日/DST 调整、行权价政策、权威参考价、
命名兼容与做市准备仍须业务、风控、清算、法务和运营签署；未完成时只能保留内部草稿。

## 2. 本轮发现并修复的问题

1. 延迟队列原来直接把到期 `PENDING` 合约改为 `TRADING`，绕过系列上市复核、公司行动、行情
   新鲜度、风险参数和交易日历。现在延迟消息与周期扫描均调用 `listContractIfEligible`，在同一事务
   锁定并重新确认合约身份、状态和全部上市门禁。
2. 相同 request key 并发首次创建会先缓存“不存在”；输掉系列锁竞争的请求可能读取负缓存并返回
   “操作不允许”。现在幂等键走无缓存数据库查询，同 key 同 payload 锁竞争直接返回赢家版本。
3. 空系列范围的并发 `FOR UPDATE` 在真实 MySQL 产生 1213。创建逻辑现在只对 1213/1205 最多
   重试5次并指数退避，普通业务错误不重试；20 路创建全部返回同一 ID 和 payload hash。
4. 系列、expiry、band 和谱系虽不可变，生成后的真实合约 `strike_price` 仍可被直接 SQL 修改。
   新迁移在数据库层禁止系列合约经济字段变化、软删除和物理删除，同时保留生命周期合法状态推进。
5. 正式 RPC 脚本此前没有安装系列迁移。现在连续执行两次系列 schema 与合约保护迁移，并输出固定
   `contract_series_capacity=` 证据行。

## 4. 关键结果

- 创建：并发数20；系列1、expiry 2、band 1；同 key 不同经济输入拒绝。
- 生成：`expected/generated/details/contracts=500/500/500/500`，Call/Put 为250/250，
  唯一 expiry/strike 对250，无重复代码或 contract ID。
- 复核：创建人不能批准生成或上市；两名生成复核人与两名上市复核人的并发调用均收敛为单一持久结果；
  成功响应丢失后的两次复核重放不新增数据。
- 失败原子性：代码碰撞系列保持 `PENDING_REVIEW`，生成数0、谱系0，仅保留预置冲突代码1；
  502 输入对应系列行0。
- 上市：复核前、缺行情、31秒陈旧行情和错误 due identity 均保持 `PENDING`；更新为新鲜行情并使用
  精确消息身份后仅目标合约进入 `TRADING`，其余499个仍为 `PENDING`。
- 全套门禁：主真实 RPC 场景108.188秒；最终
  `instructions=9240 success=9235 canceled=5 reconciled=9235 weighted_terminal=9245`，并通过
  5000 美式指派、501 实物交割、501 现金到期及三类进程强杀接管回归。
