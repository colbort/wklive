# Option 功能完整性与通用期权设计评审

## 1. 文档信息

- 评审对象：`services/option`，并核对其使用的 Asset RPC、Option Proto 和 System 定时任务
- 评审日期：2026-07-31
- 评审方式：代码、Proto、数据库结构、任务链路、单元测试和静态检查
- 评审目标：判断当前实现是否完整，以及是否达到一般中心化期权交易平台的交易、风控、行权、清算和运营要求
- 结论性质：工程与风险设计评审，不代替具体司法辖区的法律、牌照、会计或合规意见

## 2. 总体结论

**当前 `services/option` 已形成核心交易 MVP，但功能并不完善，尚未达到一般生产级期权交易和清算要求。**

现有实现的领域方向基本合理：以 Asset Option 钱包为资金事实来源，订单资金先冻结后入簿，成交后使用 outbox/inbox 更新持仓，卖方具有逐仓/组合/实物担保模式，也已经实现强平、保险/平台兜底、欧式到期、美式现金提前行权和可恢复资产指令。

但是，本轮初审发现的缺口中包含多项资金与风险正确性问题，不只是压测、监控或产品增强问题。代码整改已经覆盖以下六项 P0：钱包级风险聚合、净清算权益、行情分类时间戳、正式结算价、保证金币种和 FIFO 全量指派；当前均处于 `VERIFYING`，仍缺预生产 Asset RPC、并发、故障注入和大容量端到端验收，不能据此直接开放真实资金。

P2-004 公司行动 V1 也已完成事件版本、停牌撤单、四眼复核、后继合约、逐持仓和 margin lot
迁移代码闭环，且 MySQL 8.4 双执行与不可变触发器已通过，当前为 `VERIFYING`。5001 持仓重启、
Asset/风险/权限预生产验收完成前，
仍不得为可能发生公司行动的标的承诺自动调整能力。

仓库级可观测性现已覆盖正式结算价、组合风险版本、公司行动、合约系列、公开链配对和 OI

## 3. 已具备的能力

- Call、Put，欧式和受限的美式现金期权。
- 现金结算和严格全额担保的欧式实物交割。

- 成交使用每合约撮合序号，并通过 outbox/inbox 可靠更新持仓。
- 支持开仓、平仓、可用量冻结和订单剩余资金释放。

- 欧式自动行权，美式现金主动行权。

## 4. P0：上线阻断问题

### 4.1 风险账户与资产钱包的账户范围不一致

**初审现状（已整改）**

- 风险持仓按 `(tenant_id, user_id, account_id, settle_coin)` 分组：
  `internal/logic/task/processriskaccountslogic.go:107-110`
- 读取 Asset 余额时只传入 `(tenant_id, user_id, wallet_type, coin)`：
  `internal/logic/task/processriskaccountslogic.go:131-137`
- Asset 请求结构没有 `account_id`：
  `proto/asset/asset.proto:332-337`
- 下单直接接受并保存请求中的 `account_id`，未看到该账户归属/存在性校验：
  `internal/logic/app/placeorderlogic.go:202-225`

**影响**

同一用户如果有两个 Option `account_id`，两个风险账户都可能读取同一份钱包总资产。该余额会被重复作为权益支持不同账户的卖方头寸，导致保证金重复使用、风险率偏低和延迟强平。

**整改要求**

只能选择一种一致模型：

1. Asset 增加真实的 Option 子账户账本，所有冻结、扣减、入账和查询都携带 `account_id`；或
2. Option 风险、持仓和订单统一为用户钱包级，不再按 `account_id` 分割风险；或
3. 明确定义跨账户统一保证金池，并让订单准入、风险扫描、强平和报表全部按同一聚合键工作。

同时必须校验 `account_id` 属于当前用户，禁止客户端任意构造账户编号。

**当前结果**

Option 采用第二种方案：订单/持仓的 `account_id` 仅保留为业务归属维度，风险账户、资产镜像、组合保证金准入和下单风险状态统一到用户钱包级 `account_id=0`；自成交保护按 `user_id` 生效。历史镜像通过 `20260730_zb_option_wallet_account_mirror.sql` 合并。隔离环境的真实 Asset gRPC 已证明跨两个业务账户只生成一条风险账户和钱包镜像，冻结/释放最终差额为0；限制传播、STP、组合并发及生产消息链路仍待预生产验收。

### 4.2 风险权益公式不符合期权净清算价值

**初审现状（已整改）**

持仓未实现盈亏按 `mark - open` 或 `open - mark` 计算，风险权益再使用：

```text
equity = Asset total + unrealized PnL
```

代码位置：`internal/logic/task/processriskaccountslogic.go:145-164,214`

**问题示例**

- 空头初始资产 100，卖出期权收到权利金 5 后 Asset total 为 105。
- 标记价格仍为 5，未实现盈亏为 0。
- 当前公式得到权益 105；但平仓需要支付 5，净清算价值应为 100。

多头也存在对称问题：支付权利金后钱包余额已减少，当前公式没有把持有期权的现值作为资产加回。

**整改要求**

统一使用可对账的净清算价值：

```text
equity = Asset total
       + Σ(long quantity × mark × multiplier)
       - Σ(short quantity × mark × multiplier)
       + 其他已确认但未入账项目
```

如果使用“期初权益 + 累计盈亏”模型，则不能再把已经完成权利金收付的 Asset total 与 `mark-open` 重复组合。修复后应建立逐成交、平仓、行权、到期和强平的会计恒等式测试。

**当前结果**

风险权益已改为 `Asset total + long mark value - short mark value`，并增加 `net_option_value` 审计字段；买方权利金实际扣款成功前不创建可计价持仓。真实 Asset gRPC 已精确通过买方 `980+20=1000`、空方 `1020-20=1000` 和跨账户净值 `1000+20-10=1010`；开仓权利金—真实撮合部分平仓/主动行权/到期/无穿仓及穿仓逐仓整仓强平—资金与持仓收益 E2E 已通过。隔离 Call 的公开订单链已覆盖 LIMIT 下单、冻结前/后用户撤单、IOC 部分成交和 FOK 流动性不足：IOC 只成交1/2张并精确释放剩余10.4，FOK保持零成交且全额释放；总计60条实际执行指令全部成功对账，另1条冻结前撤单指令合法取消且不产生 Asset 流水。穿仓缺口38由保险15+平台23覆盖，保险、兜底和担保扣减提交后响应丢失均以原业务身份恢复；组合保证金及部分强平仍待实现，市价、管理强撤和其他币种路径仍待同等级验收。部分平仓成交额 15，买/卖费用 `0.6/0.3`；平仓方剩余 1 张的已实现/未实现盈亏为 `5/5`，累计费用 1.3，`total_return = realized_pnl = 3.7`。

### 4.3 标的价和期权标记价共用新鲜度时间戳

**初审现状（已整改）**

- 标的行情同步只更新 `UnderlyingPrice` 和内在价值，保留原有 `MarkPrice`/IV/Greeks，却刷新共用 `SnapshotTime`：
  `internal/logic/option/syncmarketquotelogic.go:140-146`
- 风险扫描用同一个 `SnapshotTime <= 30s` 同时判断标的价和标记价有效：
  `internal/logic/task/processriskaccountslogic.go:99-105`
- 成交只在原标记价为 0 时设置标记价：
  `internal/logic/app/app_order_match.go:322-331`

**影响**

只要标的行情持续更新，一条很久没有更新的期权标记价也会被当成新鲜价格。卖方权益、保证金和强平价格可能因此失真。

**整改要求**

- 至少拆分 `underlying_snapshot_time`、`mark_snapshot_time` 和 `greeks_snapshot_time`。
- 标记价应有明确算法和来源，例如盘口中间价、最近成交和理论价的受控组合。
- 任一关键输入过期时应停止风险降低和卖方新开仓，并触发告警；不能因为另一类行情刷新而解除过期状态。

**当前结果**

市场表已拆分 `underlying_snapshot_time`、`mark_snapshot_time`、`greeks_snapshot_time`，不可变快照增加来源类型和来源 ID，消费者按用途检查对应时间。旧数据迁移仅回填可证明的标的时间，不能以兼容 `snapshot_time` 通过卖方风险检查。合约增加显式 `greeks_max_age_seconds`：0表示未审批且不能通过新上市门禁，正数由产品/风控审批；OPT-A003 按逐合约阈值检测未配置、缺失、未来和过期。管理端合约详情分别展示三类时间、阈值和状态，不猜测默认值。当前基础清算权益模型不使用 Greeks，因此异常只阻止依赖 Greeks 的新功能并告警。

### 4.4 最终结算价没有绑定到期时点/正式窗口

**初审现状（已整改）**

`lockSettlementPrice` 在生命周期任务运行时读取当前行情，只要求该行情相对“任务当前时间”不超过 300 秒，然后以单一样本写入：

```text
SampleCount = 1
CalculationMethod = LAST_AT_EXPIRY
WindowStart = WindowEnd = market.SnapshotTime
```

代码位置：`internal/logic/task/processcontractlifecyclelogic.go:211-240`

**初审影响**

任务如果晚于到期时间运行，可以把到期后的价格锁定为最终结算价。初审实现也没有指数窗口、异常值剔除、多源确认、人工审批和更正流程；当时的 `SourceSnapshotIds` 只是当前可变行情行的描述，不是对不可变原始样本的强引用。

**整改要求**

- 每个合约必须配置正式结算指数、采样窗口、算法、精度和异常处理规则。
- 只读取不可变快照中属于 `[window_start, window_end]` 的样本。
- 设置最小样本数、来源健康度、离群点规则和源数据哈希/ID。
- 增加“计算—复核—确认—发布”状态及双人审批；更正必须新版本留痕，不覆盖旧值。
- 增加到期任务迟到、行情缺口、价格源中断和人工更正测试。

**当前结果**

生命周期在使用已确认版本前会按证据 ID 重新读取不可变快照并复算中位数；窗口、数量、JSON、
缺失/重复证据、价格或四眼信息任一不一致都会阻止创建结算批次。数据库触发器执行同类门禁、
禁止删除所有版本，监控同时识别合法人工更正并暴露历史异常。相同证据的已拒绝自动候选不会被
任务反复重建。仓库级真实 RPC 已验证：119/120/121窗口样本锁定正式价120，错误确认价121
被数据库拒绝，缺价合约不创建结算；卖方50冻结金扣20、释放30，买方入账20，最终120+80=200、
冻结0，三条指令成功并对账，生命周期重放无重复。生产调度/通知、费用、部分数量、多账户、
大批量到期和完整故障注入仍待预生产执行。仓库级 SET-001 已进一步证明扣冻结前 RPC
`Unavailable` 时 step 2不产生成功或流水；真实Asset扣款成功但响应丢失时，Option同样阻断
step 2，恢复后沿用原指令号认领唯一扣款流水，不发生二次扣款。OPS-006 已验证执行者在真实
Asset 扣款后、Option 保存结果前终止时，超龄 `PROCESSING` 自动恢复仍只认领原流水。
SET-003 已验证可用余额不足连续20次失败进入 `MANUAL_REVIEW`，缺原因或缺操作人均不能重置；
独立业务号补资后沿用原指令恢复，重置与包含原状态、20次失败和错误信息的不可变事件同事务提交。
真实容器强杀仍未覆盖。

### 4.5 实物 Call 的部分系统撤单释放了错误币种

**初审现状（已整改）**

初审时，到期撤单、强平撤单和管理端强制撤单直接使用 `order.FeeCoin`。

实物 Call 卖出开仓在下单时将 `margin_coin` 设置为 `underlying_coin`：
`internal/logic/app/placeorderlogic.go:164-173`

**影响**

系统会尝试释放结算币，而实际冻结的是标的币，可能使订单长期停留在释放中并遗留冻结担保。

**整改要求**

所有订单保证金释放、消耗和对账统一调用同一个币种解析函数，并增加实物 Call/Put 在用户撤单、到期撤单、管理撤单和异常恢复四条路径的集成测试。

**当前结果**

用户撤单、IOC/FOK 撤余、到期、强平、管理强撤和撮合买方释放均统一调用
`OptionOrderMarginCoin(order)`；该函数现只接受实际冻结的 `margin_coin`，不再回退 `FeeCoin`。
历史订单和 margin lot 按合约确定性回填，新写入由数据库和模型双重门禁，无法确定的遗留证据
通过 OPT-A032 租户水位 fail-closed。迁移双执行和真实 MySQL 币种边界已纳入仓库验收；
实物 Call/Put 的真实 Asset 冻结—释放 E2E 尚待执行。

### 4.6 美式行权指派公平性和容量（初审缺口已整改）

**初审现状（已整改）**

- 每笔行权开始前，取消该合约所有用户的活动空头平仓买单：
  `internal/logic/task/processexerciseslogic.go:66-91`
- 指派空头只查询第一页 500 条，没有继续分页：
  `internal/logic/task/processexerciseslogic.go:134-149`
- 持仓分页按 `id DESC`，即较新的持仓优先：
  `models/toptionpositionmodel.go:73-80`

**影响**

- 一名用户主动行权会影响并未被指派的其他空头用户订单。
- 超过 500 个空头账户时，系统可能错误判断可指派数量不足并永久重试。
- 当前行为不是文档所称 FIFO，也不是随机或按比例分配，缺少公开、可审计的公平规则。

**整改要求**

- 明确定义 FIFO、随机或按比例指派规则，并固定可复核的排序键/随机种子。
- 分页读取或通过数据库原子分配直到满足数量。
- 只冻结和取消实际候选空头的相关平仓数量，不能全合约取消。
- 增加 500+ 空头、部分可用、并发平仓与行权、任务重放测试。

**当前结果**

指派已按持仓建立时间、ID 升序执行 FIFO，通过 `(create_times,id)` 键集分页每次最多读取
500条，不再一次性加载全合约候选；每名候选在撤销其平仓单后重新执行当前读行锁并使用最新
可用量。仅取消实际遍历候选的相关平仓单，数量不足时事务整体回滚。专用复合索引、SQL 单测
和隔离 MySQL 1/500/501/5000 条分页容量证据已补齐。隔离环境进一步用 20 个相同客户端键
并发提交主动行权，只形成 1 笔行权和一次数量冻结；两个并发清算执行只形成 2 个 FIFO 指派、
6 条唯一资金指令和 6 条唯一 Asset 流水，全部成功且对账一致。当前真实 RPC 场景使用两个
空头，501/5000 空头真实 Asset 容量、与平仓并发竞争、多实例任务强杀仍待预生产执行。

## 5. P1：重要功能和控制缺口

### 5.1 单一坏行情会中断整轮风险扫描

初审时，风险任务先收集全部持仓，遇到任一缺失或陈旧行情立即返回；刷新任一风险组失败也立即终止。

在全局任务模式下，一个合约、账户或租户异常可能阻止后续全部账户刷新。应按租户/合约/风险账户隔离失败，记录扫描水位并告警。对坏行情账户应采取保守限制，而不是让旧风险状态继续生效。

当前已按钱包隔离行情和 Asset 刷新错误：失败钱包进入 `RESTRICTED`，其他钱包继续刷新，任务结束后
聚合返回错误以保留调度重试和告警语义。每次实际扫描另按租户输出总钱包组、失败组、失败比例和
完成时间，收集/重置阶段用有限标签 Counter；不会从存量 `RESTRICTED` 账户反推失败率。
单元测试已通过，跨租户故障注入和生产告警 E2E 尚待执行。

- 错单、异常成交撤销/更正及审计流程。

**当前结果**

- 已实现用户多/空持仓上限、合约 OI 上限和价格带。准入在用户控制行与合约行锁内完成，
  敞口覆盖持仓、活动委托以及成交后尚未由 outbox 落仓的数量。
- 已实现标记价跳变熔断：达到阈值时原子暂停合约并幂等撤销活动订单。

  账户、原成交币种、精确平衡分录，独立管理员复核后按“全部扣款、再入账”执行，案件和分录不可篡改。

  价格带拒绝另追加 `ORDER_REJECTED/ORDER_PRICE_BAND` 分子事实；组合拒单回滚后在独立事务重记审计。

因此本项为 `VERIFYING`，不能据此开放生产。系统有意不提供删除原成交的“交易 bust”；

### 5.4 组合保证金只是简化 V1

`internal/risk/portfolio.go:36-43,83-151`

其优点是确定、保守和可解释；初审时没有：

当前整改没有把该算法包装成 SPAN，而是为受限模型补齐最基本的生产治理：
参数已按租户和结算币版本化、独立管理员审批并具有明确有效期，风险账户记录实际版本，

情景损失和裸空头底线之上增加集中度与流动性附加。缺少有效批准版本时
拒绝新增组合卖方风险并限制存量风险账户。跨期限、跨标的、波动率相关性及
美式期权抵扣仍明确禁止；历史回测、独立验证和预生产回滚仍是开放功能前的外部准入证据。

### 5.5 持仓已实现盈亏口径不一致

初审时，平仓按“平仓权利金减开仓均价”记录已实现盈亏；提前行权和到期结算只记录 payoff，没有把原始权利金成本/收入纳入同一口径。

当前平仓、提前行权、到期和强平已统一保存
`trade_realized_pnl`（权利金交易毛盈亏）、
`settlement_realized_pnl`（行权/到期结算毛盈亏）、
`fee_paid` 和 `total_return`，并保持兼容字段
`realized_pnl = total_return`。多头总收益为结算 payoff 加平仓权利金收益减开仓成本及费用，
空头总收益为权利金收益减结算付款及费用；到期放弃也会把已付/已收权利金结转。

历史 `realized_pnl` 无法从旧记录可靠拆出费用与退出来源，迁移只保守归入交易毛盈亏并保持
总数不变。仓库级真实 Asset 已验证部分平仓、提前行权、到期和无穿仓逐仓整仓强平的会计恒等式。强平场景中用户保证金扣 88/释放 12，保险账户入账并冻结 80，平台费 8；原空头 `trade_realized=-60`、`fee=8`、`total_return=-68`。保险接管仓位同步承接维持保证金 40。组合保证金、穿仓保险/平台兜底和故障恢复未验收，
因此本项仍为 `VERIFYING`。

### 5.6 提前行权接口边界控制（仓库级闭环通过）

已完成：

- 用户主动行权强制 `client_exercise_id`，数据库唯一键保证并发幂等；相同键同一请求返回原行权 ID，不同请求拒绝。
- `exercise_qty` 校验合约 `qty_step`。
- 净 payoff 扣除行权费后必须为正。
- 现金结算合约具有独立 `exercise_cutoff_time`，截止时刻及之后拒绝新主动行权和新到期指令；
  完全相同的历史请求仍可幂等返回。
- 新主动行权和新到期指令只允许合约处于 `TRADING/PAUSED` 且已经上市；交易暂停不剥夺
  持有人行权权，但 `PENDING/EXPIRED/SETTLED/OFFLINE` 均拒绝。事务内锁定合约后再次校验，
  防止状态或截止时间在并发请求期间跨界。
- AUTO、DNE 和相反行权指令按持仓追加版本，旧版本留存并变为已替代；
  数据库触发器禁止原地改写经济字段、已替代状态回退及删除历史。
- AUTO 仅在每单位内在价值达到合约阈值且净收益为正时行权；DNE 放弃；
  相反行权可绕过自动阈值，但不能绕过“内在价值和净收益必须为正”。
- 现金到期结算只让实际已行权多头获得 payoff，空头按实际行权量 FIFO 承担，
  阈值以下或 DNE 持仓不会造成空头付款。
- 提前行权指派按数量同比例减少空头维持保证金；实际保证金金额仍只在对应 Asset margin lot
  指令成功后扣减或释放，避免“义务已建立但资金未成功”时提前伪造资金完成。

仓库真实 RPC 已通过：20 并发同键只生成 1 笔、同键不同数量拒绝、两个并发清算只生成一次
FIFO 指派；两个空头分别承担 1/2 张，空头总扣 120 = 多头净入 108 + 手续费 12。结合开仓权利金 30，多头/空头A/空头B总收益分别为 `78/-30/-60`，平台手续费 12，四方合计 0；最终钱包为 `178/70/140/12`，总资产 400、冻结 0，全部仓位和 margin lot 均已结清。混合 AUTO/DNE 到期只产生 1 张实际行权，空头只扣 20，多头净入 18、
手续费 2；结合两名多头各支付权利金 10，AUTO/DNE/空头总收益分别为 `8/-10/0`，平台收入 2，合计 0；最终钱包 `108/90/200/2`。4 条指令及流水唯一，批次借贷均为 20。指令经济字段改写、
已替代状态回退和删除均被数据库拒绝。

仍未完成：预生产不同键并发替换、毫秒级截止跨界、进程/容器强杀和大批量到期 E2E；
实物交割的 DNE/相反指令在违约处置规则闭环前明确拒绝。

### 5.7 实物交割违约处置未闭环

卖方采用全额担保，但买方行权款/标的资产没有在持仓期间预冻结。到期时任一买方扣款失败，会阻塞同一结算批次的后续入账。

整改采用可保持守恒的配对独立交割单元。到期按多空持仓 FIFO 拆分为一多一空的数量单元，
资产执行顺序固定为“多头应交资产扣减 → 空头担保扣减 → 双方应收资产入账”。
资金指令仍以结算批次号聚合和对账，但步骤屏障以交割单元号隔离：

```text
单元 A：买方扣款成功 → 卖方担保扣减成功 → 买方/卖方入账
单元 B：买方扣款失败 → 补资/人工复核（不得入账）
```

因此单元 B 不阻塞单元 A，且不存在先入账后补资金。失败后安全默认是补资期结束转违约人工复核；
平台不垫资、不自动没收、不自动放弃。补资时长、通知、罚则及退款/继续交割/拍卖等最终经济处置
仍须产品、风控、清算和法务批准，批准前实物产品继续禁止上线。

## 11. 外部基准

本评审使用以下公开资料作为一般期权和生产风险系统的设计基准：

- [OCC：Characteristics and Risks of Standardized Options](https://www.theocc.com/company-information/documents-and-archives/options-disclosure-document)：标准化期权的行权、指派、结算和风险披露。
- [CME：SPAN Methodology Overview](https://www.cmegroup.com/solutions/risk-management/performance-bonds-margins/span-methodology-overview.html)：组合保证金需要考虑价格、波动率、时间和其他风险因子的压力情景。
- [CFTC：Margin Requirements for Uncleared Swaps](https://www.cftc.gov/LawRegulation/FederalRegister/finalrules/2020-01065.html)：用于参考保证金与产品/组合风险匹配、相关性抵扣和模型独立验证原则。
- [CFTC：System Safeguards Testing Requirements](https://www.cftc.gov/LawRegulation/FederalRegister/finalrules/2016-22413.html)：用于参考容量、可靠性、灾备和系统保障测试。
- [CME：Money Calculations for Futures and Options](https://www.cmegroup.com/clearing/files/CME-Money-Calculations-Futures-and-Options.pdf)：用于参考期权现金金额和结算计算。
- [Cboe：Complex Orders](https://www.cboe.com/us/options/trading/complex_orders/)：用于参考复杂订单的净价、比例和整体执行语义。
- [Cboe：Complex Book Process](https://www.cboe.com/document/tech-spec/document/technical-specifications/cboe-titanium-u.s.-options-complex-book-process)：用于参考复杂策略簿与执行边界。

## 12. 最终建议

保留当前 Option 的领域模型、Asset 单一账本、先冻结后撮合、可靠资产指令、结算批次和风险账户方向，但应把当前状态明确标记为 **Development / Restricted MVP**。

在 P0 全部修复并完成端到端验收前：

- 不开放真实资金卖方；
- 不开放组合保证金；
- 不开放美式主动行权；
- 不开放实物交割；
- 不开放复杂/组合订单；
- 不把 `mmp`、复杂订单、组合保证金或正式结算能力作为生产已完成功能对外发布。

修复顺序应优先保证资金与估值正确，其次完成到期/行权正确性，再补交易控制和生产运营能力。
