现有实现的领域方向基本合理：以 Asset Option 钱包为资金事实来源，订单资金先冻结后入簿，成交后使用 outbox/inbox 更新持仓，卖方具有逐仓/组合/实物担保模式，也已经实现强平、保险/平台兜底、欧式到期、美式现金提前行权和可恢复资产指令。

- Call、Put，欧式和受限的美式现金期权。

## 4. P0：上线阻断问题

### 4.1 风险账户与资产钱包的账户范围不一致

**初审现状（已整改）**

- 风险持仓按 `(tenant_id, user_id, account_id, settle_coin)` 分组：
  `internal/logic/task/processriskaccountslogic.go:107-110`
- 读取 Asset 余额时只传入 `(tenant_id, user_id, wallet_type, coin)`：
  `internal/logic/task/processriskaccountslogic.go:131-137`
- Asset 请求结构没有 `account_id`：
  `proto/asset/asset.proto:332-337`
- 下单直接接受并保存请求中的 `account_id`，未看到该账户归属/存在性校验：
  `internal/logic/app/placeorderlogic.go:202-225`

**影响**

同一用户如果有两个 Option `account_id`，两个风险账户都可能读取同一份钱包总资产。该余额会被重复作为权益支持不同账户的卖方头寸，导致保证金重复使用、风险率偏低和延迟强平。

**整改要求**

只能选择一种一致模型：

1. Asset 增加真实的 Option 子账户账本，所有冻结、扣减、入账和查询都携带 `account_id`；或
2. Option 风险、持仓和订单统一为用户钱包级，不再按 `account_id` 分割风险；或
3. 明确定义跨账户统一保证金池，并让订单准入、风险扫描、强平和报表全部按同一聚合键工作。

同时必须校验 `account_id` 属于当前用户，禁止客户端任意构造账户编号。

**当前结果**

Option 采用第二种方案：订单/持仓的 `account_id` 仅保留为业务归属维度，风险账户、资产镜像、组合保证金准入和下单风险状态统一到用户钱包级 `account_id=0`；自成交保护按 `user_id` 生效。历史镜像通过 `20260730_zb_option_wallet_account_mirror.sql` 合并。隔离环境的真实 Asset gRPC 已证明跨两个业务账户只生成一条风险账户和钱包镜像，冻结/释放最终差额为0；`RESTRICTED`钱包下两个业务账户均无法增险，跨账户相反订单执行cancel-taker且0成交/1审计事件，清理后4条资金指令成功对账、钱包100/冻结0。组合跨账户并发及生产消息链路仍待预生产验收。

### 4.2 风险权益公式不符合期权净清算价值

**初审现状（已整改）**

持仓未实现盈亏按 `mark - open` 或 `open - mark` 计算，风险权益再使用：

```text
equity = Asset total + unrealized PnL
```

代码位置：`internal/logic/task/processriskaccountslogic.go:145-164,214`

**问题示例**

- 空头初始资产 100，卖出期权收到权利金 5 后 Asset total 为 105。
- 标记价格仍为 5，未实现盈亏为 0。
- 当前公式得到权益 105；但平仓需要支付 5，净清算价值应为 100。

多头也存在对称问题：支付权利金后钱包余额已减少，当前公式没有把持有期权的现值作为资产加回。

**整改要求**

统一使用可对账的净清算价值：

```text
equity = Asset total
       + Σ(long quantity × mark × multiplier)
       - Σ(short quantity × mark × multiplier)
       + 其他已确认但未入账项目
```

如果使用“期初权益 + 累计盈亏”模型，则不能再把已经完成权利金收付的 Asset total 与 `mark-open` 重复组合。修复后应建立逐成交、平仓、行权、到期和强平的会计恒等式测试。

**当前结果**

风险权益已改为 `Asset total + long mark value - short mark value`，并增加 `net_option_value` 审计字段；买方权利金实际扣款成功前不创建可计价持仓。真实 Asset gRPC 已精确通过买方 `980+20=1000`、空方 `1020-20=1000` 和跨账户净值 `1000+20-10=1010`；开仓权利金—真实撮合部分平仓/主动行权/到期/逐仓及组合整仓/部分数量强平—资金与持仓收益 E2E 已通过。隔离 Call 的普通订单链已覆盖 LIMIT、带保护价 MARKET、POST_ONLY、IOC、FOK及冻结前/后用户撤单：IOC只成交1/2张并释放10.4，FOK不足保持零成交，MARKET预留12后消费10.4并释放1.6，POST_ONLY会吃单时零成交撤销、不会吃单时入簿。现金USDT管理强撤已统一复用控制撤单事务并写入逐单不可变操作审计；20轮公开撤单/资金冻结竞争均恰好一个撤单请求获胜，订单、钱包和指令身份收敛。资产执行器进一步通过独立进程`SIGKILL`和两个新进程竞争接管：30秒Redis租约自然到期，只有一个接管者进入Asset并认领原流水。除竞态外固定95条指令成功对账、2条冻结前合法取消；竞态门禁为`success + 2*canceled = 139`，最近一次全套运行是135条成功、2条合法取消。穿仓缺口38由保险15+平台23覆盖，保险、兜底和担保扣减提交后响应丢失均以原业务身份恢复。组合保证金以两个账户级空头顺序清算，10条资金指令全部对账；每次只消费高于剩余初始保证金的抵押，完成后重算才创建下一笔，最终余量释放且冻结归零。逐仓风险扫描已按`qty_step`自动选择严格恢复健康的最小数量，并按FIFO比例拆分margin lot；2张仓位自动清算1张的5条指令全部对账，资金前数量预占和重放通过。组合部分数量也以同一情景模型自动从2张选择1张，消费抵押44、收取强平费4，4条清算指令全部对账，刷新后源仓剩1张/抵押560且钱包恢复健康。保险接管库存不会递归进入客户强平；持仓数、最早接管时间、标的等价数量、标记价值、绝对Delta、24小时临期/已到期和行情失效指标/规则已实现。受控主动退出已实现为不可变申请、独立复核和确定性 `ADMIN + BUY + CLOSE + REDUCE_ONLY + IOC`：2张申请在只有1张深度时成交1张、撤销1张，20路并发执行只形成1个订单/客户端键，4条资金指令/流水闭合，保险仓剩1张/保证金40。自动Delta对冲未实现；跨币种折算仍关闭。部分平仓成交额 15，买/卖费用 `0.6/0.3`；平仓方剩余 1 张的已实现/未实现盈亏为 `5/5`，累计费用 1.3，`total_return = realized_pnl = 3.7`。

### 4.3 标的价和期权标记价共用新鲜度时间戳

**初审现状（已整改）**

- 标的行情同步只更新 `UnderlyingPrice` 和内在价值，保留原有 `MarkPrice`/IV/Greeks，却刷新共用 `SnapshotTime`：
  `internal/logic/option/syncmarketquotelogic.go:140-146`
- 风险扫描用同一个 `SnapshotTime <= 30s` 同时判断标的价和标记价有效：
  `internal/logic/task/processriskaccountslogic.go:99-105`
- 成交只在原标记价为 0 时设置标记价：
  `internal/logic/app/app_order_match.go:322-331`

**影响**

只要标的行情持续更新，一条很久没有更新的期权标记价也会被当成新鲜价格。卖方权益、保证金和强平价格可能因此失真。

**整改要求**

- 至少拆分 `underlying_snapshot_time`、`mark_snapshot_time` 和 `greeks_snapshot_time`。
- 标记价应有明确算法和来源，例如盘口中间价、最近成交和理论价的受控组合。
- 任一关键输入过期时应停止风险降低和卖方新开仓，并触发告警；不能因为另一类行情刷新而解除过期状态。

**当前结果**

市场表已拆分 `underlying_snapshot_time`、`mark_snapshot_time`、`greeks_snapshot_time`，不可变快照增加来源类型和来源 ID，消费者按用途检查对应时间。旧数据迁移仅回填可证明的标的时间，不能以兼容 `snapshot_time` 通过卖方风险检查。合约增加显式 `greeks_max_age_seconds`：0表示未审批且不能通过新上市门禁，正数由产品/风控审批；OPT-A003 按逐合约阈值检测未配置、缺失、未来和过期。管理端合约详情分别展示三类时间、阈值和状态，不猜测默认值。当前基础清算权益模型不使用 Greeks，因此异常只阻止依赖 Greeks 的新功能并告警。

### 4.4 最终结算价没有绑定到期时点/正式窗口

**初审现状（已整改）**

`lockSettlementPrice` 在生命周期任务运行时读取当前行情，只要求该行情相对“任务当前时间”不超过 300 秒，然后以单一样本写入：

```text
SampleCount = 1
CalculationMethod = LAST_AT_EXPIRY
WindowStart = WindowEnd = market.SnapshotTime
```

代码位置：`internal/logic/task/processcontractlifecyclelogic.go:211-240`

**初审影响**

任务如果晚于到期时间运行，可以把到期后的价格锁定为最终结算价。初审实现也没有指数窗口、异常值剔除、多源确认、人工审批和更正流程；当时的 `SourceSnapshotIds` 只是当前可变行情行的描述，不是对不可变原始样本的强引用。

**整改要求**

- 每个合约必须配置正式结算指数、采样窗口、算法、精度和异常处理规则。
- 只读取不可变快照中属于 `[window_start, window_end]` 的样本。
- 设置最小样本数、来源健康度、离群点规则和源数据哈希/ID。
- 增加“计算—复核—确认—发布”状态及双人审批；更正必须新版本留痕，不覆盖旧值。
- 增加到期任务迟到、行情缺口、价格源中断和人工更正测试。

**当前结果**

合约现可配置权威来源、正式窗口、`MEDIAN` 算法和最小样本数；生命周期任务只读取窗口内不可变快照，先生成 `PENDING` 版本，由不同操作人复核发布。更正创建 `manual-correction/MANUAL` 新版本并保留被替代版本。

生命周期在使用已确认版本前会按证据 ID 重新读取不可变快照并复算中位数；窗口、数量、JSON、
缺失/重复证据、价格或四眼信息任一不一致都会阻止创建结算批次。数据库触发器执行同类门禁、
禁止删除所有版本，监控同时识别合法人工更正并暴露历史异常。相同证据的已拒绝自动候选不会被

## 5. P1：重要功能和控制缺口

### 5.1 单一坏行情会中断整轮风险扫描

初审时，风险任务先收集全部持仓，遇到任一缺失或陈旧行情立即返回；刷新任一风险组失败也立即终止。

在全局任务模式下，一个合约、账户或租户异常可能阻止后续全部账户刷新。应按租户/合约/风险账户隔离失败，记录扫描水位并告警。对坏行情账户应采取保守限制，而不是让旧风险状态继续生效。

#### 5.5.1 逐仓部分强平选量与边界

对逐仓空头，移交数量 `q` 后，源钱包总资产减少接管成本和强平费，同时空头市值负债减少相同的接管成本，
所以净权益只减少强平费；维持保证金按数量线性下降。记当前缺口为
`D = maintenance - equity`，单位数量维持保证金为 `m`，单位数量强平费为 `f`，则必须选择满足
`(m - f) × q > D` 的最小 `qty_step` 整数倍。等号仍处于强平边界，必须再增加一个步长；若单仓全部数量
仍不足，只处置该仓并在资金、仓位和margin lot完成后重新扫描，不并行创建第二笔。

该公式只适用于同结算币的逐仓线性保证金。组合保证金的情景风险非线性：先按“完整移除后维持保证金下降最多、
同值取较小 position_id”选仓，再按合约 `qty_step` 从小到大调用同一已审批情景模型重算剩余组合；只有在组合
维持保证金下降、剩余初始保证金不超过当前抵押，且扣除本次强平费后的权益严格大于“逐仓维持保证金 + 剩余组合
维持保证金”时才选中该数量。等号不算恢复健康；超过 100000 个步长时 fail closed。若没有部分数量恢复健康，
则处置所选整仓，完成后重新扫描钱包。执行前必须按当前行情、配置、仓位和抵押再次运行相同模型，不能信任触发时
数量。该实现已通过边界和上限单测；真实 Asset RPC 已验证2张自动选择1张、4条清算指令成功对账、刷新后账户
恢复健康且未创建第二笔。margin lot 抵押币种不同于结算币时，在没有获批
汇率来源、折扣、滑点和故障回退模型前直接拒绝。保险接管账户属于系统库存，
保留风险展示但排除客户递归强平。租户级数量、标记价值、绝对Delta、临期及行情失效告警已实现；公开订单簿
只减仓IOC退出也已实现，但这不等于库存风险已经解决：生产逐合约限额、额外可用权利金来源、角色授权、
预生产通知复演和Delta对冲仍是生产阻断项。

### 5.7 实物交割技术处置已闭环，最终经济规则待批准

卖方采用全额担保，但买方行权款/标的资产没有在持仓期间预冻结。原始批次级步骤屏障会让任一买方扣款失败阻塞同批其他用户；该技术缺口现已通过单元级屏障修复。

整改采用可保持守恒的配对独立交割单元。到期按多空持仓 FIFO 拆分为一多一空的数量单元，
资产执行顺序固定为“多头应交资产扣减 → 空头担保扣减 → 双方应收资产入账”。
资金指令仍以结算批次号聚合和对账，但步骤屏障以交割单元号隔离：

```text
单元 A：买方扣款成功 → 卖方担保扣减成功 → 买方/卖方入账
单元 B：买方扣款失败 → 补资/人工复核（不得入账）
```

因此单元 B 不阻塞单元 A，且不存在先入账后补资金。失败后安全默认是补资期结束转违约人工复核；
平台不垫资、不自动没收、不自动放弃。补资时长、通知、罚则及退款/继续交割/拍卖等最终经济处置

- [CFTC：System Safeguards Testing Requirements](https://www.cftc.gov/LawRegulation/FederalRegister/finalrules/2016-22413.html)：用于参考容量、可靠性、灾备和系统保障测试。
- [CME：Money Calculations for Futures and Options](https://www.cmegroup.com/clearing/files/CME-Money-Calculations-Futures-and-Options.pdf)：用于参考期权现金金额和结算计算。
- [Cboe：Complex Orders](https://www.cboe.com/us/options/trading/complex_orders/)：用于参考复杂订单的净价、比例和整体执行语义。
- [Cboe：Complex Book Process](https://www.cboe.com/document/tech-spec/document/technical-specifications/cboe-titanium-u.s.-options-complex-book-process)：用于参考复杂策略簿与执行边界。

## 12. 最终建议

保留当前 Option 的领域模型、Asset 单一账本、先冻结后撮合、可靠资产指令、结算批次和风险账户方向，但应把当前状态明确标记为 **Development / Restricted MVP**。

在 P0 全部修复并完成端到端验收前：

- 不开放真实资金卖方；
- 不开放组合保证金；
- 不开放美式主动行权；
- 不开放实物交割；
- 不开放复杂/组合订单；
- 不把 `mmp`、复杂订单、组合保证金或正式结算能力作为生产已完成功能对外发布。

修复顺序应优先保证资金与估值正确，其次完成到期/行权正确性，再补交易控制和生产运营能力。
