# Option 业务设计评审

## 1. 文档信息

- 评审对象：`services/option`
- 评审日期：2026-07-30
- 当前阶段：核心交易闭环已实现，高级风险与交割能力仍在开发
- 评审范围：合约、行情、委托、撮合、持仓、资金、行权、到期结算
- 不在本次范围：独立的 `services/staking` 质押理财业务

## 2. 评审结论

本评审最初发现资金账本、卖方风险、订单状态、行权清算和结算价格尚未形成一致闭环。P0、P1、P2 问题现已完成代码实现；卖方逐仓保证金、风险扫描、强平接管、保险基金补亏及美式现金提前行权也已形成异步清算链路。

当前上线判断仍为：**不通过生产真实资金验收**。原因已经从“核心设计不闭环”转变为“高级风险兜底和生产级验证尚未完成”。

以下六项是本次评审的原始阻断项，目前均已有对应实现，具体完成度见第 11 节：

1. 统一资产账本，消除统一资产与 option 本地账户之间的双账。
2. 禁止资产冻结成功前的订单进入订单簿。
3. 明确卖方模式并建立相应的担保或保证金模型。
4. 行权和到期结算必须形成多空守恒的清算指令。
5. 建立可信、不可变、可审计的结算价。
6. 将到期处理改造成可重试、可恢复、可对账的状态机。

## 4. 初始阻断性问题

本节保留首次评审时发现的问题及设计要求，描述的是整改前基线，不代表第 11 节记录的当前实现状态。

### 4.1 统一资产和 option 本地账户形成双账

下单冻结调用统一资产服务，钱包类型为 `WALLET_TYPE_OPTION`；成交、行权和结算却只修改 `t_option_account` 和 `t_option_bill`。

当前缺失：

- 成交后消费买方冻结资金；
- 将权利金实际划转给卖方；
- 部分成交后按未成交数量保留冻结；
- 成交价格优于委托价格时释放差额；
- 行权和结算时在统一资产账本完成收付；
- option 本地流水与资产流水的关联及对账；
- 跨服务失败后的补偿与重试。

本地账户允许从不存在的账户直接应用负数变动，因此可能创建负余额账户。该行为无法证明用户真实资产足以支付。

#### 设计要求

- 统一资产服务必须是资金事实来源。
- `t_option_account` 只能作为查询镜像或风险快照，不能独立创造资金。
- 每次资金动作必须生成唯一资产指令。
- 资产指令至少包含：
  - `tenant_id`
  - `user_id`
  - `wallet_type`
  - `coin`
  - `biz_no`
  - `instruction_no`
  - `scene`
  - `amount`
  - `status`
  - `retry_count`
- 资金操作必须支持幂等重放和最终对账。

### 4.2 未完成资产冻结的订单可能被撮合

当前流程先将委托以 `PENDING` 状态提交到数据库，再调用资产服务冻结。撮合查询会直接选择 `PENDING` 和 `PART_FILLED` 委托。

并发情况下，另一笔订单可以在冻结完成前将该委托作为 maker 成交。

#### 建议状态

```text
CREATED
  -> FUNDING
  -> PENDING
  -> PART_FILLED
  -> FILLED

FUNDING -> REJECTED
PENDING/PART_FILLED -> CANCELING -> CANCELED
PENDING/PART_FILLED -> EXPIRING -> EXPIRED
```

只有 `PENDING` 和 `PART_FILLED` 可以进入订单簿。资产冻结成功事件负责将 `FUNDING` 推进到 `PENDING`。

### 4.3 卖出开仓保证金模型不成立

当前所有开仓统一冻结：

```text
委托价格 × 委托数量 × 合约乘数
```

该公式最多可以作为买方权利金上限，不能作为卖方开仓保证金：

- 裸卖 call 的风险理论上不封顶；
- 裸卖 put 的最大损失主要由行权价决定；
- 当前没有初始保证金、维持保证金、风险率、追加保证金或强平流程。

#### 首版建议

优先选择受限产品：

- 欧式；
- 现金结算；
- 自动行权；
- 仅限价单；
- 用户仅允许买入开仓及卖出平仓；
- 卖方由平台或全额担保做市账户承担。

如果必须开放用户卖出开仓，则必须先实现完整的保证金、强平、保险基金和穿仓处理体系。

### 4.4 行权没有形成多空资金守恒

主动行权当前直接给多头增加 payoff，没有在同一清算链路中扣减对应空头资金或消耗空头保证金。

资金守恒应满足：

```text
多头净收入
+ 空头净收入
+ 平台手续费收入
+ 舍入调整
= 0
```

行权不应直接将某个持仓视为资金来源。应先形成合约级或清算批次级净额，再生成多方资产指令。

### 4.5 部分行权与自动行权冲突

自动行权逻辑只要发现持仓存在任意行权记录，就跳过整个持仓。

例如：

```text
初始持仓：10
手动行权：2
到期剩余：8
```

剩余 8 张可能不会进入自动行权。

幂等条件应改为：

- 以 `position_id + settlement_batch_id` 唯一；
- 根据持仓剩余数量计算；
- 累计已行权数量不得超过持仓原始可行权数量；
- 自动行权只处理尚未行权且尚未冻结的剩余数量。

### 4.6 结算价格不可控

到期结算直接读取 `t_option_market.underlying_price`。行情不存在时使用 0，但流程仍可能完成结算并将合约标记为 `SETTLED`。

风险包括：

- 使用过期行情；
- 使用非权威行情；
- 行情缺失时错误结算；
- put 在价格为 0 时产生异常巨额 payoff；
- 无法说明最终结算价的来源和计算过程；
- 已完成结算无法安全更正。

#### 结算价快照要求

建议增加不可变结算价记录：

| 字段 | 含义 |
| --- | --- |
| `contract_id` | 合约 |
| `price_source` | 权威行情来源 |
| `window_start/end` | 取价窗口 |
| `sample_count` | 有效样本数 |
| `calculation_method` | TWAP、指数价或指定规则 |
| `delivery_price` | 最终结算价 |
| `source_snapshot_ids` | 原始快照依据 |
| `version` | 结算价版本 |
| `status` | 待计算、待确认、已确认、已废弃 |
| `confirmed_by/at` | 审批信息 |

价格缺失、不新鲜或样本不足时，合约必须停留在待结算或失败状态。

## 5. 重要功能缺口

### 5.1 订单类型语义未实现完整

已有 `LIMIT`、`MARKET`、`POST_ONLY`、`IOC`、`FOK` 枚举，但当前执行路径基本按限价委托处理。

要求：

- `MARKET`：使用保护价或最大成交金额，不能依赖普通限价字段。
- `POST_ONLY`：若会立即成交，应拒绝或按明确配置取消。
- `IOC`：立即成交后取消剩余数量。
- `FOK`：必须预检查完整可成交数量，否则不得产生任何成交。

首版若不支持，应从 API 和后台配置中移除或显式拒绝，不能静默降级为限价单。

### 5.2 参数校验不足

下单至少需要校验：

- side、position effect 和 order type 必须是有效枚举；
- 价格必须大于 0；
- 数量必须满足 `min_order_qty`、`max_order_qty`；
- 数量必须满足 `qty_step`；
- 价格必须满足 `price_tick`；
- 当前时间必须位于交易窗口；
- 合约不可删除或下线；
- 平仓数量不得超过可用持仓；
- `reduce_only` 必须与持仓及开平方向一致；
- `account_id` 必须属于当前用户。

合约创建还需要校验：

- 行权价、合约单位、乘数、步长均为正数；
- 最大数量不小于最小数量；
- `list_time < expire_time <= deliver_time`；
- 现金和实物结算所需币种配置完整；
- 上市后关键经济参数不可修改。

### 5.3 现金与实物结算能力不一致

协议声明支持 `CASH` 和 `PHYSICAL`，当前业务统一按现金 payoff 处理。

在实现标的资产锁定、行权资金锁定、标的划转和失败补偿前，不应允许创建或启用实物交割合约。

### 5.4 `deliver_time` 未形成真实生命周期

建议生命周期明确为：

```text
PENDING
  -> TRADING（list_time）
  -> EXPIRED（expire_time，停止交易）
  -> SETTLING（锁定结算价并清算）
  -> SETTLED（deliver_time 后且资金指令全部完成）
```

暂停和下线应作为运营状态，不能替代正常的到期清算状态。

### 5.5 手续费与风险字段只有数据结构

已有成交手续费、行权手续费、持仓保证金、维持保证金和风险率字段，但未形成可执行规则。

未实现的能力不应通过非零字段或管理配置对外宣称支持。

### 5.6 撮合架构仅适合原型

当前撮合运行在下单 RPC 的数据库事务中。随着并发增加，会面临：

- 同一合约缺少明确的全序；
- 数据库锁竞争；
- RPC 超时但实际已成交；
- 撮合和资产状态跨服务不一致；
- 故障恢复及事件重放困难。

建议后续演进为按合约分区的单写撮合模型：

```text
订单资金确认
  -> 订单命令日志
  -> 按 contract_id 分区
  -> 单分区顺序撮合
  -> 成交事件
  -> 持仓与资金结算消费者
```

## 6. 推荐目标架构

### 6.1 服务职责

| 服务/模块 | 事实来源 |
| --- | --- |
| option contract | 合约规则和生命周期 |
| market | 权威标的行情 |
| matching | 委托顺序、订单簿和成交 |
| option position | 持仓和行权数量 |
| clearing | 成交、行权及到期净额 |
| asset | 余额、冻结、扣款、入账及资产流水 |
| reconciliation | option 业务与资产账本对账 |

### 6.2 成交资金流

```text
买方下单
  -> 冻结最大权利金及费用
  -> 冻结成功
  -> 订单进入订单簿
  -> 成交
  -> 消费本次成交对应冻结
  -> 卖方收到权利金
  -> 收取双方手续费
  -> 释放价格改善及终态剩余冻结
  -> 更新业务账务镜像
```

每一步必须由稳定的 `instruction_no` 保证幂等。

### 6.3 到期结算状态机

```text
WAITING_PRICE
  -> PRICE_LOCKED
  -> CALCULATING
  -> INSTRUCTIONS_CREATED
  -> ASSET_PROCESSING
  -> RECONCILING
  -> DONE

任一步骤 -> FAILED -> RETRYING
```

合约只有在所有资产指令完成且对账通过后才能进入 `SETTLED`。

### 6.4 建议新增核心记录

- `t_option_asset_instruction`
- `t_option_settlement_price`
- `t_option_settlement_batch`
- `t_option_settlement_detail`
- `t_option_outbox`
- `t_option_inbox`
- `t_option_reconciliation_result`

## 7. 分阶段实施计划

### P0：账务和并发安全

- 确定统一资产为唯一账本。
- 增加订单资金确认状态。
- 实现冻结、消费、释放和收付资产指令。
- 修复成交失败后的冻结补偿。
- 禁止本地 option 账户产生无来源资金。
- 增加资金守恒断言和对账任务。

验收标准：

- 任意成交、撤单、超时和重试后，统一资产账本余额守恒。
- 未冻结成功的订单永远不能成交。
- 同一资产指令重复执行不会重复扣款或入账。

### P1：受限产品闭环

- 仅支持欧式现金结算。
- 仅支持限价单。
- 禁止用户裸卖开仓。
- 实现结算价锁定和自动行权。
- 修复部分手动行权后的剩余数量处理。
- 实现合约级多空净额清算。

验收标准：

- 多头收益、空头支出、费用和舍入严格守恒。
- 行情缺失或过期时不会完成结算。
- 生命周期任务重复执行不会重复行权或重复入账。

### P2：交易能力完善

- IOC、FOK、POST_ONLY 和市场保护单。
- 手续费配置和计费。
- 成交价格改善释放。
- 独立撮合序列及事件化持仓结算。
- 运营暂停、恢复、强制撤单及异常结算工具。

### P3：卖方保证金与高级产品

- 卖方初始和维持保证金。
- 组合风险和抵扣规则。
- 追加保证金与强平。
- 保险基金和穿仓处理。
- 美式期权。
- 实物交割。

## 8. 测试与验收矩阵

### 8.1 委托与撮合

- 相同 `client_order_id` 并发下单。
- 冻结超时、失败和成功回调乱序。
- 部分成交后撤单。
- 成交价优于委托价。
- maker/taker 并发撤单和成交竞争。
- 自成交防护。
- 合约到期与撮合并发。

### 8.2 持仓

- 买入开仓、卖出平仓。
- 禁止无持仓平仓。
- 多个平仓委托冻结数量竞争。
- 部分成交后的可用、冻结和总持仓守恒。

持仓必须满足：

```text
position_qty = available_qty + frozen_qty
```

### 8.3 行权和结算

- 价内、平价和价外 call/put。
- 部分手动行权后自动行权剩余数量。
- 自动行权任务重复执行。
- 结算价缺失、过期和版本变更。
- 结算资产指令部分成功后重试。
- 合约级多空资金守恒。
- 舍入精度和最小币种单位。

### 8.4 故障恢复

- 数据库提交成功但 RPC 返回超时。
- 资产冻结成功但 option 服务宕机。
- 成交已提交但资产消费者宕机。
- 结算批次处理中重启。
- MQ 重复、乱序和延迟消息。

当前产品门禁：

- `SELLER_MARGIN_MODE_DISABLED` 可用于不开放卖方开仓的受限产品；
- `SELLER_MARGIN_MODE_ISOLATED` 已具备逐仓保证金和保险账户强平接管，但 ADL/穿仓分摊完成前不得用于真实资金；
- `EXERCISE_STYLE_AMERICAN + SETTLEMENT_TYPE_CASH` 已开放设计能力，主动行权只允许在上市后、到期前且权威行情不超过 30 秒时发起；
- `SELLER_MARGIN_MODE_PORTFOLIO` 和 `SETTLEMENT_TYPE_PHYSICAL` 仍在合约校验层拒绝；
- 风险扫描使用 Asset Option 钱包总资产作为权威权益来源，行情超过 30 秒即停止刷新，不使用旧价格降低风险要求；
- 强平阈值触发后创建幂等强平记录，撤销风险用户活动委托后，按标记价将空头义务转移至保险账户；
- 保险基金不足时进入人工处理，不会把未覆盖亏损伪装为成功；当前不会自动进行 ADL 或社会化损失分摊；
- 美式主动行权存在待处理记录时，到期任务不得进入最终结算，防止同一持仓重复清算。

### 11.1 仍然阻断生产上线的事项

1. 实现并评审保险基金不足后的 ADL、穿仓分摊或明确的全额平台兜底制度。
2. 对成交、强平、提前行权、到期结算执行 RPC 超时、部分成功、重复消息、进程重启等故障注入。
3. 建立未完成资产指令、人工处理强平、待处理行权、保险基金余额和对账差异的生产监控。
4. 完成大批量到期结算、风险扫描和撮合并发压测。
5. 在开放美式现金产品前补齐行权指派和异常资金指令的专用运营查询与恢复入口。

因此，当前设计对于“欧式现金 + 统一资产账本”的受限产品方向是合理的；逐仓卖方和美式现金的代码结构也已具备闭环基础，但尚不能等同于完成生产验收。组合保证金与实物交割继续保持显式禁用是合理选择。
