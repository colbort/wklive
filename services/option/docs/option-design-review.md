# Option 业务设计评审

## 1. 文档信息

- 评审对象：`services/option` 及其依赖的 `services/asset`、Admin/App API 和管理端
- 评审日期：2026-07-30
- 当前阶段：核心交易、清算和风险链路已实现，处于故障验收与产品规则定稿阶段
- 评审范围：合约、委托、撮合、持仓、资金、保证金、强平、行权、到期结算和运营恢复
- 不在范围：独立的 `services/staking` 质押理财业务；Staking 未完成不影响本文对 Option 的判断

## 2. 结论

当前 Option 的领域拆分和资金清算方向是合理的，首次评审发现的“双账、未冻结订单可成交、卖方无保证金、行权不守恒、结算价不可信、结算不可恢复”等结构性问题已经有对应实现。

但当前仍不建议直接通过生产真实资金验收。原因不再是核心代码没有闭环，而是以下生产级条件尚未完成：

1. 缺少覆盖成交、强平、提前行权和双币交割的长时间故障注入与全链路验收。
2. 缺少大批量到期、组合风险扫描和热点合约撮合压测。
3. 未完成生产告警接入、阈值校准和 7×24 处置演练。
4. 组合保证金 V1 仍是确定性价格情景模型，不是包含波动率曲面和跨期限相关性的完整 SPAN 模型。
5. 实物交割虽然具备严格的“先扣后付”步骤屏障，但买方交割资产不足时会阻塞整个批次；上线前必须明确补资时限、放弃行权、违约处置或拆分批次规则。
6. 撮合仍在下单 RPC 的数据库事务中执行，适合当前规模和验收环境，尚未证明可以承载高并发生产流量。

因此，分产品判断如下：

| 产品范围 | 设计判断 | 当前门禁 |
| --- | --- | --- |
| 欧式现金、禁止用户卖出开仓 | 合理，核心闭环完整 | 通过故障、压测、监控验收后可灰度 |
| 欧式/美式现金、逐仓卖方 | 合理，风险与清算链路已闭环 | 需完成强平和保险/兜底故障演练 |
| 欧式现金、组合保证金 V1 | 在明确限制下合理 | 需完成模型校准、回测和压力测试 |
| 欧式严格担保实物交割 | 交收方向合理，但产品违约规则未定稿 | 暂不开放真实资金 |
| 美式组合保证金、裸卖实物交割 | 不合理/未支持 | 合约校验显式拒绝 |

## 3. 当前能力边界

### 3.1 合约组合

代码使用 Proto enum 表达产品策略，不使用魔法数字作为业务配置。

| 维度 | 已支持 | 限制 |
| --- | --- | --- |
| 期权类型 | `OPTION_TYPE_CALL`、`OPTION_TYPE_PUT` | 未知枚举拒绝 |
| 行权方式 | 欧式、现金结算美式 | 实物只允许欧式；组合保证金只允许欧式 |
| 结算方式 | `CASH`、严格担保 `PHYSICAL` | 实物必须启用严格交割策略 |
| 订单类型 | LIMIT、MARKET、POST_ONLY、IOC、FOK | MARKET 使用保护价；FOK 先检查完整流动性 |
| 卖方模式 | DISABLED、ISOLATED、PORTFOLIO、COVERED_DELIVERY | COVERED_DELIVERY 仅用于实物 |
| 穿仓策略 | MANUAL_REVIEW、PLATFORM_BACKSTOP | 平台兜底必须配置专用平台账户 |

合约上市后，币种、行权价、乘数、时间、费用、卖方模式、风险参数和交割策略等经济字段不可修改。

### 3.2 核心数据对象

当前完整 schema 共 26 张表。除合约、行情、订单、成交、持仓、行权和结算外，关键可靠性对象包括：

| 对象 | 职责 |
| --- | --- |
| `t_option_asset_instruction` | 记录冻结、扣冻结、释放、可用余额扣减和入账指令 |
| `t_option_settlement_price` | 保存权威结算价、取价窗口、样本和确认信息 |
| `t_option_settlement_batch` | 驱动可恢复的结算状态机 |
| `t_option_settlement_detail` | 保存逐持仓现金或双币交割审计明细 |
| `t_option_outbox` / `t_option_inbox` | 成交后持仓事件的可靠投递和消费幂等 |
| `t_option_reconciliation_issue` | 记录资产流水或余额镜像不一致 |
| `t_option_margin_lot` | 记录逐仓、组合池或实物担保的冻结批次 |
| `t_option_risk_account` | 保存账户权益、保证金、风险率和组合风险快照 |
| `t_option_liquidation` | 保存强平、保险基金和平台兜底处置结果 |
| `t_option_exercise_assignment` | 保存美式提前行权的空头 FIFO 指派 |

`t_option_account` 和 `t_option_bill` 只作为 Asset 事实账本的查询镜像与审计记录，不能独立创造余额。

## 4. 关键设计评审

### 4.1 资金和订单准入

资金事实来源统一为 Asset 的 Option 钱包。下单先进入 `FUNDING`，冻结成功后才能进入 `PENDING` 订单簿；冻结失败进入 `REJECTED`。成交、撤单、到期撤单、行权、强平和结算均通过唯一 `instruction_no` 的异步资产指令执行。

该设计解决了两个原始高风险问题：

- 未完成冻结的订单不能成为 maker；
- RPC 超时或任务重放不会重复扣款、释放或入账。

资产指令执行后会按 Asset 流水核对租户、用户、钱包、币种、业务场景、方向和金额，再同步 Option 账户镜像。差异写入对账问题表，不能静默当作成功。

### 4.2 撮合和成交后处理

当前支持 LIMIT、MARKET、POST_ONLY、IOC、FOK，包含价格/数量步长、交易窗口、持仓可用量、reduce-only 和账户归属校验。每个合约具有独立撮合序号，成交后通过 outbox/inbox 更新持仓和保证金批次。

当前架构的主要限制是撮合仍运行在下单 RPC 的数据库事务中。它简化了当前一致性，但热点合约会形成锁竞争，RPC 延迟也会随订单簿深度增加。规模扩大后建议演进为：

```text
资金准入
  -> 按 contract_id 分区的订单命令
  -> 单分区顺序撮合
  -> 成交事件
  -> 持仓与清算消费者
```

### 4.3 手续费和资金守恒

maker、taker 和行权费均由合约配置；非零费率必须配置收费用户和账户。成交价格优于买方保护价时释放差额。

现金行权和到期结算遵守：

```text
多头总收入 + 平台费用 = 空头保证金消耗 + 空头可用余额扣减 + 保险/兜底
```

结算批次在资产指令成功并完成对账后才能进入 `DONE`，合约才能标记为 `SETTLED`。

### 4.4 结算价

到期不会直接把当前行情当作最终结果。系统生成不可变结算价记录，保存价格来源、窗口、样本数、算法、源快照、版本及确认时间。价格缺失、过期或样本不足时，结算保持等待或失败，不能用 0 价完成。

这一设计合理；上线前仍需由业务和风控确认正式指数源、异常样本剔除、停牌和人工改价审批制度。

## 5. 卖方风险设计

### 5.1 逐仓保证金

卖出开仓根据标的价、行权价、合约乘数以及初始/维持/最低保证金率计算保证金。成交后保证金按批次绑定空头持仓；平仓时 FIFO 消耗或释放。风险任务使用 Asset Option 钱包作为权威权益来源，行情超过 30 秒时不会使用旧价格降低风险要求。

触发强平后：

1. 幂等创建强平记录并撤销风险账户活动订单；
2. 按标记价把空头义务转移到保险账户；
3. 消耗用户保证金及必要的可用余额；
4. 保险基金覆盖剩余缺口；
5. 合约配置为平台兜底时，剩余缺口记入 `OPTION_BACKSTOP` 平台账户，允许形成可审计负债；
6. 配置为人工处理或兜底失败时进入人工状态，不伪装成成功。

平台兜底比自动 ADL 更适合当前产品阶段，但它不是“没有损失”。必须为负余额设限额、审批、补足时限和财务对账。

### 5.2 组合保证金 V1

`PORTFOLIO_RISK_METHOD_EXPIRY_SCENARIO_V1` 的规则是：

- 只在相同标的、结算币和到期日内抵扣；
- 情景点包含 0、当前价、2 倍当前价、配置的上下冲击价以及全部行权价；
- 以当前权利金价值减各情景到期价值的最大损失作为情景风险；
- 再以净裸空头最低保证金作为下限；
- 初始保证金用于订单准入，维持保证金用于风险扫描；
- 风险增加型活动卖单存在时不释放组合池保证金；
- 待成交买单不提前作为保护腿。

该模型具有确定、可解释、可审计和不跨期限错误抵扣的优点，适合作为保守 V1；其限制也必须明确：

- 不使用隐含波动率曲面、vega/gamma 情景和流动性附加；
- 不提供跨期限、跨标的或统计相关性抵扣；
- 市场驱动的保证金上升由风险扫描和强平处理，不是同步自动追保；
- 美式提前行权可能移除保护腿，因此组合保证金仅允许欧式现金合约。

上线前必须使用历史行情和极端情景回测，确认冲击率、最低保证金率、扫描周期和清算延迟覆盖。

## 6. 行权设计

欧式合约在到期时自动行权；美式现金合约允许上市后、到期前主动行权。主动行权使用不超过 30 秒的权威行情，先预留多头可行权数量，再按 FIFO 指派空头。

每个指派记录对应空头保证金消耗/释放和必要的余额补扣；多头净收益与平台费用在所有前序扣款成功后才入账。存在未完成主动行权时，到期任务不能进入最终结算，从而避免同一持仓重复清算。

后台已提供行权详情、指派和资产指令查看，以及失败行权重试入口。仍需通过高并发部分行权、临近到期竞争和资产部分成功故障测试。

## 7. 实物交割设计

实物 V1 只允许：

- 欧式；
- 自动行权；
- `PHYSICAL_DELIVERY_POLICY_STRICT`；
- `SELLER_MARGIN_MODE_COVERED_DELIVERY`；
- 标的币与结算币不同；
- 行权费为 0；
- Call 卖方全额冻结标的币，Put 卖方全额冻结行权款。

价内交割方向如下：

| 合约 | 多头步骤 1 | 多头步骤 2 | 空头步骤 1 | 空头步骤 2 |
| --- | --- | --- | --- | --- |
| Call | 扣行权款 | 收标的币 | 扣冻结标的币 | 收行权款 |
| Put | 扣标的币 | 收行权款 | 扣冻结行权款 | 收标的币 |

所有步骤 1 指令成功前，整个 `settlement_no` 下的步骤 2 均不可执行。价外合约不交割，释放空头担保。系统校验多空交割数量、行权款和空头担保币种/金额，并将交割币、数量、付款币和金额保存到逐持仓审计明细。

该“全局先扣后付”屏障可以防止先向收款方创造资产，方向正确；但它带来批次级阻塞风险。当前买方交割资产在到期时从可用余额扣减，没有在持有期间全程冻结。任一价内买方余额不足时，已成功的步骤 1 会保持幂等状态，步骤 2 等待补资和重试。

生产开放前必须选择并实现明确规则之一：

1. 交割前窗口预冻结买方资产；
2. 余额不足视为放弃行权并制定罚则；
3. 平台垫付并形成可追偿负债；
4. 将批次拆为可独立失败且仍保持资产守恒的交割单元。

在规则定稿前，实物交割应保持测试或白名单状态。

## 8. 恢复、对账和运营

当前已有：

- 通用失败资产指令重试；
- 成交事件重放；
- 强平详情及重试；
- 行权详情、指派详情及专用重试；
- 结算批次、逐持仓明细、资产指令详情及单指令专用重试；
- 结算资产指令按 `biz_no + step_no` 的全局步骤屏障；
- 资产流水核对和对账问题记录；
- 租户写权限校验和独立后台权限点。

生产监控至少应接入以下信号：

| 信号 | 建议告警 |
| --- | --- |
| PENDING/FAILED 资产指令最老年龄 | 超过任务周期 3 倍告警 |
| MANUAL_REVIEW 资产指令数量 | 大于 0 立即告警 |
| OPEN 对账问题数量和最老年龄 | 大于 0 或持续增长告警 |
| FAILED/长期 PROCESSING 结算批次 | 大于 0 立即告警 |
| 待处理行权和指派最老年龄 | 接近到期或超过任务周期告警 |
| LIQUIDATING/BANKRUPT 风险账户 | 大于 0 告警 |
| 保险基金余额和 `OPTION_BACKSTOP` 余额 | 低于限额/负债超过限额告警 |
| 行情快照年龄 | 超过 30 秒停止风险降档并告警 |
| outbox/inbox 重试和积压 | 持续增长告警 |

代码和后台记录已提供这些信号的数据来源，但告警平台、阈值、通知链路和处置演练属于部署工作，当前尚未完成。

## 10. 上线门禁

### 10.1 可进入受限灰度前

- [x] Asset 是唯一资金事实来源。
- [x] 未冻结成功的订单不能成交。
- [x] 核心资产指令具备幂等、重试和流水对账。
- [x] 结算价有不可变快照和审计依据。
- [x] 现金行权、结算和强平具有资金守恒检查。
- [x] 不支持的合约组合被显式拒绝。
- [x] 后台具备强平、行权和结算恢复入口。
- [ ] 核心链路故障注入连续通过。
- [ ] 生产监控、阈值、通知和运行手册完成。
- [ ] 目标流量压测通过。

### 10.2 开放组合保证金前

- [ ] 完成历史回测和极端情景校准。
- [ ] 明确扫描频率、行情中断和追加保证金 SLA。
- [ ] 对组合池并发下单、平仓、到期和强平做全链路验收。
- [ ] 产品文档明确“不跨期限/标的抵扣”和“不支持美式”的限制。

### 10.3 开放实物交割前

- [ ] 定稿买方交割资产不足规则并实现。
- [ ] 完成双币余额不足、部分成功、重启和人工重试演练。
- [ ] 完成交割前通知、补资窗口和客服/运营流程。
- [ ] 只对白名单合约和账户灰度。

## 11. 最终建议

保留当前领域模型、统一资产账本、异步资产指令、结算批次、逐仓卖方和平台全额兜底设计。近期产品主路径建议仍以“欧式现金 + 禁止卖出开仓或逐仓卖方”为主。

组合保证金可以作为受限 V1 继续验收，不应宣传为完整跨期限组合保证金。实物交割代码可用于联调和故障演练，但在买方不足资产规则定稿前不应对真实资金开放。

当前最优先工作不是继续增加产品枚举，而是完成故障注入、监控告警、容量测试，以及组合风险和实物违约规则的业务签字。
